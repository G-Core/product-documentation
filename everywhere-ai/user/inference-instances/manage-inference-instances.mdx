An inference instance is started, stopped, and reconfigured from this page. Access, logs, monitoring, and deletion are on the same page.

Navigate to **Inference** > **Inference Instances** to see all instances in the project.

![Inference Instances list showing deployed instances with name, type, regions, and deployment status](/images/docs/everywhere-ai/user/inference-instances/manage-inference-instances/inference-instances-list-2.png)

The **Deployment status** column shows **Provisioning** while containers are still starting, then **Active** or **Stopped**. Expand a row using the chevron to see the pod count per region and a quick **Endpoint** link.

## Start and stop an instance

Click an instance name to open its detail view. **Actions** stops or starts the instance: **Stop** while it is running, **Start** while it is **Stopped**. A stopped instance keeps its configuration, but its containers no longer run, and the endpoint on **Overview** is not served.

![Instance detail view with the Actions menu, Overview tab, deployment status, and Endpoint link](/images/docs/everywhere-ai/user/inference-instances/manage-inference-instances/inference-instances-detail-2.png)

## Update the container image

Open the **Container image** tab to change the container the instance runs.

Select **Public Registry** to pull a public image, or **Private Registry** to use credentials. Enter the image reference in the **Image** field and set the **Container port** the application listens on. Enable **Add authorization** if the registry requires a pull secret, or **Set startup command** to override the default entry point. Click **Save changes** to apply.

## Access the endpoint

For an active instance, an **Endpoint** link appears next to the region row — on the instances list (expand the row using the chevron) and on the **Overview** tab. Copy the URL from either location.

## Manage API key authentication

Open the **API key authentication** tab to control which API keys grant access to the inference endpoint.

Select one or more keys from the **API Keys** dropdown. If no project-level key exists yet, click **Add new API Key** to create one in **Inference** > **API Keys**, then return and attach it. Click **Save changes** to apply.

If no API keys are attached, the endpoint accepts requests without authentication. When at least one key is attached, include it in the `Authorization` header of every request:

```bash
curl https://<endpoint-url>/ \
  -H "Authorization: Bearer <API_KEY>"
```

## Update instance settings

Open the **Settings** tab to adjust how the instance is deployed, scaled, and configured. Click **Save changes** at the bottom to apply any change.

![Settings tab showing Regions, Flavor, and Autoscaling limits sections](/images/docs/everywhere-ai/user/inference-instances/manage-inference-instances/inference-instances-settings.png)

**Compute and placement** — **Regions** controls which regions run the workload; the currently deployed region cannot be removed while the instance is running, so stop it first to change regions. **Flavor** changes the vCPU and RAM allocated per pod.

**Scaling and health** — **Autoscaling limits** set the minimum and maximum pod count. **Global** uses the same limits for every selected region. **Custom** sets those limits separately for each region. **Cooldown period** and **Polling interval** control how quickly the instance reacts. Add CPU or GPU **Autoscaling triggers** to scale on utilization thresholds. **Health checks** enable liveness, readiness, or startup probes — liveness restarts unhealthy pods, the readiness probe keeps the pod from receiving traffic until it is ready, and startup delays the other probes until initialization completes.

**Runtime** — **Environment variables** are injected into the container at startup. **Storage** attaches a project volume to persist data across replica restarts. **Read timeout** is the maximum seconds the gateway waits for a response before returning 504.

## Interpret a 502 or 504 response

A failed request can point to an instance configuration problem, separate from API key authentication.


<Info>
A 502 response can indicate that the gateway cannot reach the application. Check that the **Container port** matches the port the application listens on.

A 504 response indicates that the gateway did not receive a response within the allowed time. Check the logs and increase **Read timeout** if the workload needs more time.
</Info>


## View deployment logs

Open the **Logs** tab. Logs remain available after pod restarts, container crashes, scale-to-zero events, and pod deletions.

Use the time range, the **Level** filter, and the region filter to narrow results. Click **Export logs** to download the current view.

Each log entry includes a **Source** field identifying the pod role:

- For Dynamo-based deployments: `router`, `prefill`, `decode`, or similar graph component names.
- For MultiNode workloads: `leader` or `worker`.
- For standard Deployment workloads, the **Source** field is empty.

## Monitor resource usage

Open the **Monitoring** tab to track **CPU Usage**, **Memory Usage**, **GPU Utilization**, and **GPU Memory Utilization** for the running containers. Adjust **Time Range** for the period needed and use **Refresh** to control how often the graphs update. When the engine is vLLM or SGLang, the same tab adds engine-specific metrics.

## Delete an instance

Deleting an instance removes the deployment and its logs. An attached project volume stays in the project and is not deleted. To delete the instance, open the **Delete** tab and click **Delete deployment**.
