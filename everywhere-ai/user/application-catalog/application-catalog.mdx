Catalog models come with a preconfigured container, runtime, and model weights. Deploying a catalog model creates an [inference&nbsp;instance](/everywhere-ai/user/inference-instances/manage-inference-instances) with an HTTP endpoint. Depending on the model, the endpoint accepts OpenAI-compatible requests or requests to the model-specific API.

| Approach | What is already chosen | Use when |
|----------|------------------------|----------|
| Application Catalog | Model, runtime, and weights | The model is already in the catalog |
| Custom inference instance | None — the container and the runtime have to be supplied | The model or the runtime is not in the catalog |

The catalog includes text and multimodal LLMs, and models for image generation, embedding, reranking, speech recognition, text-to-speech, safety, and video. The list changes as models are added, so open **Inference** > **Application Catalog** to see the current set.

## Deploy a model

Each card shows **Min config**, the smallest flavor that can start the model. If the project does not have enough quota for that flavor, the card names the required flavor, and deployment stays unavailable until the quota covers it.

![Application catalog with category filters and minimum configuration on each model card](/images/docs/everywhere-ai/user/application-catalog/application-catalog/application-catalog-list.png)

<Steps>

<Step title="Choose a model the project can run">

Select a model in the catalog to open its page. The model page lists each **Application module** and its **Minimum flavor**. **Deploy Application** stays disabled in two cases:

- **Capacity unavailable** — the project needs quota for the flavor named in the message.
- **No suitable configuration** — no flavor on the cluster can run the model. Contact an administrator.

**License** opens the vendor's terms for that model, and the form does not add a separate acceptance step. When the button is enabled, click **Deploy Application**.

![Model page with application modules, the minimum flavor, and Deploy Application](/images/docs/everywhere-ai/user/application-catalog/application-catalog/application-catalog-model-detail.png)

</Step>

<Step title="Name the instance and pick a region">

The instance name is how the deployment is listed under **Inference Instances**, and the name is part of the endpoint host.

Under **Regions**, select a region marked **Available**, which means that region has capacity for the flavor. **Show out of stock** lists regions where the available capacity is not enough for this flavor, so the model cannot be placed there.

![Deploy form showing Instance name field and Regions selector with Show out of stock option](/images/docs/everywhere-ai/user/application-catalog/application-catalog/deploy-general.png)

</Step>

<Step title="Configure the runtime and resources">

**Serving topology** and **Runtime** together decide how the model is placed. The form shows only the combinations that model supports.

**Single node** runs each replica on one node. With **Native**, the replica serves the model directly from one **Model workers** pool. With **Dynamo**, requests are routed across workers that scale independently: a **Decode worker** generates the response tokens, and a **Dynamo router** distributes requests among them. Each pool has its own flavor and its own **Min** and **Max**.

![Dynamo runtime with a decode worker pool and a Dynamo router](/images/docs/everywhere-ai/user/application-catalog/application-catalog/deploy-dynamo.png)

**Multi-node** places each replica on a fixed group of nodes, so a model that does not fit on one node can start. The flavor line shows how many nodes are in the group and their combined memory. **Native** keeps the **Model workers** pool. **Dynamo** replaces that pool with a **Decode worker** and a **Dynamo router**.

**P/D disaggregation** separates prompt processing and token generation. Prefill workers process prompts and build the KV cache, while decode workers generate response tokens. This topology uses **Dynamo** only. The form states a recommended balance between the pools. A **Dynamo router** sends requests to the workers, and a pool can require a minimum number of servers.

![P/D disaggregation with prefill and decode pools and a recommended balance](/images/docs/everywhere-ai/user/application-catalog/application-catalog/deploy-pd-disaggregation.png)

**E/P/D disaggregation** adds an **Encode worker** that encodes the input before prefill. It also uses **Dynamo**, states its own recommended balance across the three pools, and can require a minimum number of servers in each pool.

A flavor is the GPU, CPU, and memory for one unit of a pool. On **Single node**, that unit is one replica. On **Multi-node**, the same flavor is applied to each node in the replica group. Each Dynamo pool has its own flavor. The flavor list starts with the minimum configuration shown on the model page; larger flavors require quota for the additional resources.

**Min** and **Max** are set on each pool. **Min** is the number of replicas of that pool created at start, and **Max** is the upper bound. Both start at 1. Each additional replica consumes the resources of that pool's flavor.

When a model defines them, **Chunked prefill** and **Prefix caching** appear as parameters and start enabled.

Chunked prefill splits a long prompt into chunks. The GPU can run other requests between those chunks.

Prefix caching reuses a repeated prompt prefix, so later requests that start with the same text do not process that prefix again. Both settings can be disabled independently when required by the workload.

![Topology and compute settings with flavor, replica counts, and module parameters](/images/docs/everywhere-ai/user/application-catalog/application-catalog/deploy-application-modules.png)

</Step>

<Step title="Configure access to the model">

**Expose** gives the module its own public HTTPS endpoint. With **Expose** off, the module is reachable only from other modules in the same instance.

Open WebUI provides a browser chat for an LLM. Turning it on adds a module that needs 2 vCPU and 4 GiB, with its own **Expose** switch.

Until a key exists, the selector shows 0/0. Click **Add new API Key** to create one, or select keys that already exist; several keys can be attached to one instance.


<Warning>
With no API key attached, the endpoint accepts requests that do not authenticate. With a key attached, a request without that key is rejected.
</Warning>


![API Keys section with key selector and Add new API Key button](/images/docs/everywhere-ai/user/application-catalog/application-catalog/deploy-api-keys.png)

</Step>

<Step title="Review the summary and deploy">

The **Summary** panel shows the name, the region, and any selected API keys. Check the configuration, then click **Deploy application** once the required fields are set.


<Warning>
The instance is listed under **Inference Instances** while **Deployment status** is **Provisioning**. If no replicas start, open **Logs** on that instance.
</Warning>


</Step>

</Steps>

## Call the model endpoint

Once the instance reaches **Active**, it appears under **Inference** > **Inference Instances**, with the endpoint URL on the **Overview** tab. From there, a catalog deployment supports the same [management&nbsp;features](/everywhere-ai/user/inference-instances/manage-inference-instances) as a custom inference instance: scaling, keys, monitoring, and logs.

Send an attached key in the Authorization header. Omit the header when no key is attached.

For a text-generation model that exposes the OpenAI-compatible API, send a chat completion to `/v1/chat/completions`. Set `model` to the application name on the endpoint row.

```bash
curl -X POST https://<endpoint-url>/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <API_KEY>" \
  -d '{
    "model": "<application-name>",
    "messages": [{"role": "user", "content": "Hello"}]
  }'
```
