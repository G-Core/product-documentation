Everywhere AI provides managed Slurm clusters for multi-node training, long-running compute jobs, and parallel workloads. A job goes to Slurm with the compute resources it needs, rather than starting on a selected machine. Slurm then finds suitable resources in the cluster and schedules the job for execution.

Jobs enter the cluster through a **login node**, which provides SSH access for submitting and managing them. The actual computation runs separately on **worker nodes**. Workers with the same hardware are grouped into worker node sets, so a cluster can provide different CPU and GPU resources for different workloads.

**Partitions** determine how jobs use these resources. A partition exposes selected worker node sets as a queue and applies its own scheduling rules: job-time limits, node limits, and priority. When the requested resources are available in the selected partition, Slurm assigns the job to its worker nodes and starts execution.

The nodes still need access to the same data even when different workers execute different jobs. For this reason, login and worker nodes share a **persistent volume** mounted at a common path. Datasets can be prepared from the login node and then accessed by the workers that run the job, while job outputs remain available after the computation finishes.

## Cluster statuses

A cluster moves through several states as it is created or changed:

| Status | Description |
|--------|-------------|
| **Pending** | The cluster is being provisioned and resources are being allocated. |
| **Ready** | All nodes are running and the cluster can accept jobs. |
| **Updating** | A change to the cluster is being applied (node count, flavor, or configuration). |
| **Unknown** | The cluster state cannot be determined. Check the **Logs** tab for details. |

Login nodes have their own status in addition to the overall cluster status:

| Status | Description |
|--------|-------------|
| **Active** | The node is running and accepting SSH connections. |
| **Updating** | A change is being applied. If the cluster has another active login node, it can be used to access the cluster. |
| **Deleting** | The node is being removed. The cluster remains accessible through other login nodes. |


<Info>
To connect over SSH, the cluster must be **Ready** and the login node must be **Active**.
</Info>
