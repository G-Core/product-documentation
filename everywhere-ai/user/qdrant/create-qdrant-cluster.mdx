A Qdrant cluster runs one or more replicas of the database. Each replica stores a complete copy of the data, so the replica count determines both redundancy and the query capacity available to the cluster. Each replica also receives its own persistent storage, while applications connect through the cluster endpoint.

## Create a cluster

Navigate to **Managed Databases** > **Qdrant vector DB** and click **Create Qdrant DB**. When the list already contains clusters, the button is **Create Qdrant Cluster**.

![Empty Qdrant list with the Create Qdrant DB button](/images/docs/everywhere-ai/user/qdrant/create-qdrant-cluster/qdrant-empty-state-full.png)

<Steps>

<Step title="Select the deployment location and compute">

The region determines where replicas run and cannot be changed after creation. It also determines which compute flavors are available — select the region closest to the applications that will query the database.

Within that region, select a flavor for the expected dataset and query load. More RAM allows more vectors to stay in memory, improving query performance. If a flavor shows **Out of stock**, it is temporarily unavailable in the selected region.

Finally, select the Qdrant version to deploy. Like the region, the version cannot be changed after cluster creation.

</Step>

<Step title="Configure replicas and storage">

For high availability, enable **High Availability** and set the replica count to at least three; the cluster can then continue operating if one replica becomes unavailable. A single replica is sufficient when its query capacity meets the expected load and downtime from a replica failure is acceptable.

Regardless of the replica count, each replica stores its own complete copy of the database and therefore requires persistent storage for vectors, indexes, and metadata. Storage type cannot be changed after creation, but storage size can be increased later. Use the <a href="https://qdrant.tech/documentation/guides/capacity-planning" target="_blank">capacity planning guide</a> to estimate the initial size based on vector count and dimensions.

</Step>

<Step title="Configure access">

By default, the cluster is accessible only within the internal network. Enable **Expose cluster** to add a public endpoint for clients outside that network. API keys authenticate requests to the public endpoint. Select an existing key, or click **Add new API Key**. The secret is shown once, when the key is created.

![Expose cluster enabled with an API key selected](/images/docs/everywhere-ai/user/qdrant/create-qdrant-cluster/qdrant-expose-api-keys.png)

</Step>

<Step title="Create the cluster">

Enter a cluster name. The name becomes part of the connection endpoint and cannot be changed after creation.

Click **Create Qdrant vector DB cluster**.

![Cluster appears with Initializing status after creation](/images/docs/everywhere-ai/user/qdrant/create-qdrant-cluster/qdrant-list-with-initializing.png)

After creation, the cluster appears in the cluster list with **Initializing** status while its replicas are provisioned and synchronized. When provisioning finishes, the status changes to **Ready** and the cluster can accept connections.

</Step>

</Steps>
