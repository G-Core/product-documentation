## Quick start: push a test live stream

<p>Use **PUSH** when your encoder, broadcast software, app, or automation agent sends the live stream to Gcore. Use **PULL** when Gcore must connect to your public origin URL and fetch the stream from your server.</p>

```text
PUSH:
Your encoder (ffmpeg/OBS/etc.)  --->  Gcore ingest  --->  Transcoding + CDN  --->  HTML player

PULL:
Your public origin URL  <---  Gcore ingest  --->  Transcoding + CDN  --->  HTML player
```

<p>For a first quick test, use PUSH with RTMP: it is the most common encoder workflow and requires only an ingest URL. Replace the URL with your stream's `push_url` in the command below. It generates a test video pattern and a test audio tone, encodes them as H.264/AAC, and pushes the stream to Gcore:</p>

```sh
ffmpeg -re \
  -f lavfi -i testsrc2=size=1280x720:rate=30 \
  -f lavfi -i sine=frequency=1000:sample_rate=48000 \
  -c:v libx264 -preset veryfast -tune zerolatency -pix_fmt yuv420p \
  -b:v 3000k -maxrate 3000k -bufsize 6000k -g 30 -keyint_min 30 \
  -x264-params "scenecut=0:bframes=0" \
  -c:a aac -b:a 128k -ar 48000 \
  -f flv "rtmp://vp-push-ed1.gvideo.co/in/12345?aaabbbcccddd"
```

<p>Expected result in the Control Panel:</p>

<Frame>
  ![FFmpeg test stream execution result](/images/docs/streaming-platform/live-streaming/create-a-live-stream/streaming-ffmpeg-test.png)
</Frame>

<p>For AI agents and automated backends, use this default flow:</p>

<p>1. Create a live stream with `pull: false`, RTMP ingest, and a 720p H.264-compatible transcoding setup.</p>
<p>2. Read `push_url` and `iframe_url` from the stream API response.</p>
<p>3. Start ffmpeg with the command above and replace the example RTMP URL with `push_url`.</p>
<p>4. Wait for the stream to become active (up to 15 seconds) and for playback initialization to finish.</p>
<p>5. Return `iframe_url` to the user as the HTML player link.</p>

## PUSH Ingest

### Live Ingesting

<p>Live ingesting is the process of sending a live video and audio stream from your source (encoder, camera, or app) into the Streaming Platform. The ingest point is the server endpoint that first receives the stream before it is processed (transcoded, packaged, or distributed via CDN).</p>

<p>In PUSH mode, your encoder initiates the connection to the platform ingest server. You configure the encoder with a target URL and stream key, and the server listens for that incoming connection. The push token is the secret part of the ingest URL. It authenticates the stream source for RTMP/RTMPS, SRT, and WebRTC WHIP ingest. Only one push token exists for a stream at a time, and the token must be protected like any other credential. Anyone with a valid push URL can try to publish to that stream. To rotate the token, use the [Reset push token](/api-reference/streaming/streams/reset-live-stream-push-token) API method.</p>

<p>Protocols supported for PUSH ingest typically include:</p>

- RTMP/RTMPS â€” Widely supported in encoders and streaming software.
- SRT â€” Secure and reliable, recommended for contribution over the Internet.
- WebRTC WHIP â€” Low-latency contribution from browsers or apps.

<Info>
  Only one ingest protocol type can be used for a live stream at a time. For example, if you start pushing RTMP and then try to push WebRTC WHIP simultaneously, the transcoding process will fail.

  Example of server response after sending a second stream:

  ```text
  [out#0/flv @ 0x600003934000] Error muxing a packet
  [out#0/flv @ 0x600003934000] Task finished with error code: -32 (Broken pipe)
  [out#0/flv @ 0x600003934000] Terminating thread with return code -32 (Broken pipe)
  [out#0/flv @ 0x600003934000] Error writing trailer: Broken pipe
  [out#0/flv @ 0x600003934000] Error closing file: Broken pipe
  ```
</Info>

<p>To use PUSH ingest, you must:</p>

<p>1. Select one protocol (RTMP, SRT, or WebRTC WHIP).</p>
<p>2. Configure your encoder with the server ingest URL and your unique stream key or token.</p>
<p>3. Ensure network/firewall allows outbound TCP (for RTMP/RTMPS) and UDP (for SRT, WebRTC).</p>

<Info>
  The origin stream provided by your encoder must strictly comply with the input parameters and codec requirements described in the [Input Parameters and Codecs](/streaming/live-streams-and-videos-protocols-and-codecs/input-parameters-and-codecs) documentation.

  Only streams that follow these specifications (supported protocols, video/audio codecs, profiles, GOP structure, and bitrate constraints) can be accepted by the ingest servers and reliably transcoded for further distribution. Any deviation from the documented requirements may cause the connection to be rejected or lead to unstable transcoding and delivery.
</Info>

### PUSH Link Formats

<p>PUSH ingest URLs are returned in the stream object and are also available in the control panel. Use the exact URL for the protocol selected in the stream settings:</p>

| Protocol | Field | Format |
| --- | --- | --- |
| RTMP/RTMPS | `push_url`, `backup_push_url` | `rtmp://rtmp.domain.com/in/{stream_id}?{push_token}` |
| RTMP/RTMPS (legacy cameras) | `push_url`, `backup_push_url` | `rtmp://rtmp.domain.com/in/{stream_id}/{push_token}` |
| SRT | `push_url_srt`, `backup_push_url_srt` | `srt://srt.domain.com:5001?streamid={stream_id}#{push_token}` |
| WebRTC WHIP | `push_url_whip` | `https://whip.domain.com/{stream_id}_{push_token}/whip` |

<p>Examples:</p>

```text
rtmp://rtmp.domain.com/in/1234567?aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
srt://srt.domain.com:5001?streamid=1234567#aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
https://whip.domain.com/1234567_aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa/whip
```

<p>Legacy RTMP cameras that don't support query strings in the URI accept an alternative path-based format, where the push token is a path segment instead of a query parameter:</p>

```text
rtmp://rtmp.domain.com/in/1234567/aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
```

<p>For enterprise projects, the ingest URL format can be adapted to existing business or encoder requirements. For example, if your current workflow already uses this style:</p>

```text
rtmp(s)://<ip:port>/app/<uuid>
```

<p>Gcore can provide a compatible format such as:</p>

```text
rtmp://vp-push-anx1.gvideo.co/app/76ac4a8b-5ff3-9028-2a4b-a31a23e5900a
```

<p>Contact your account manager or support team if you need a custom ingest URL format.</p>

### Reset the PUSH Token

<p>Reset the push token if it was exposed, shared with the wrong encoder, or needs to be rotated by your security process. After a reset:</p>

- The old token is immediately invalidated.
- The new token is returned by the API and becomes available in the control panel.
- Encoders that still use the old URL will be rejected.
- The platform tries to terminate active primary and backup ingest connections automatically.

<Info>
  Token reset affects active broadcasting. Plan token rotation during a maintenance window or be ready to restart the encoder with the new ingest URL.
</Info>

<p>To reset the push token, open the stream settings and click **Reset token**. See the REST API tab for API examples.</p>

### Failover with Primary and Backup Ingest Points for PUSH

<p>In most cases 1 primary point is used for broadcasting. Multiple points are needed for large broadcasts with multiple backups.
 Streaming Platform offers a special failover mechanism for RTMP and SRT origin streams. You can push primary and backup origin streams simultaneously to organize a backup plan.</p>

<p>Use for RTMP/S:</p>

- `push_url` â€“ as primary
- `backup_push_url` - as backup

<p>Use for SRT:</p>

- `push_url_srt` â€“ as primary
- `backup_push_url_srt` â€“ as backup

<p>**PUSH fallback algorithm:**</p>

<p>1. Primary stream active. Primary always takes priority over the backup stream.</p>
<p>2. When the primary stream fails and is unavailable for more than 3 seconds, then fallback process begins (the backup stream must be available and online):</p>
   1. New transcoding started for the backup stream
   2. End-viewers will be without stream data for Â±15 seconds
<p>3. When the primary stream is restored, a timer starts counting the time the primary stream has been active. Primary must be available for at least 60 consecutive seconds before a transition to the primary begins:</p>
   1. New transcoding started for the primary stream
   2. End-viewers will be without stream data for Â±15 seconds

### PUSH Ingest Limits

<p>Pay attention to rules of ingest server behavior for security reasons:</p>

<p>1. After a connection is established with a valid stream key, the server registers it as active. While this session remains active, any subsequent connection attempts using the same stream key will be rejected. Ingest protocol does not provide error codes for this case, so rejections occur silently. To verify whether a stream is currently active, use UI or API.</p>
<p>2. The server also enforces a connection rate limit. If too many connection attempts are made in a short period, new attempts will be denied. To avoid triggering the limiter, allow at least 10 seconds between connection attempts.</p>

<Info>
  1 connection and 1 protocol can be used at a single moment in time per unique stream key input. Trying to send 2\+ connection requests at once, or 2\+ protocols at once will not lead to a result.

  For example, if you start pushing primary RTMP and backup RTMP to the same single `push_url` simultaneously, the transcoding process will fail.
</Info>

## PULL

### Failover with Multiple Source URIs for PULL

<p>"PULL URL" field can contain 1 link, or many at once. In most cases 1 point is used. Multiple points are needed for large broadcasts with multiple backups. You can specify multiple addresses separated by a space (" "), so you can organize an extra-backup plan.</p>

<p>Example #1:</p>

```text
rtmp://encoder.example.com/live/stream123
```

<p>Example #2:</p>

```text
rtmp://encoder1.example.com/live/stream123 rtmp://encoder2.example.com/live/stream123_backup srt://encoder3.example.com:9000?mode=caller&latency=1000000&streamid=stream123
```

<p>In the Customer Portal, open a live stream's settings, enable **PULL**, and paste the origin URL (or multiple URLs separated by a space) into the **PULL URI** field.</p>

<p>To reset the push token, open the stream settings and click **Reset token**.</p>

<p>**PULL fallback algorithm:**</p>

<p>1. Stream #1 is active</p>
<p>2. If stream #1 is unavailable and is missing for more than Â±3 seconds, then the next stream #2 is taken from the "PULL URI" and transition to the next backup source begins:</p>
   1. A new transcoding for the backup stream is started.
   2. End viewers will be without stream data for Â±15 seconds.
   3. If this stream #2 is also interrupted, the above algorithm will be repeated for the next backup stream. In this case, the specified addresses will be selected one by one using round robin algorithm. If the first address does not respond, then the next one in the list will be automatically requested, returning to the first and so on in a circle. No worries, if only 1 link is specified in "PULL URI", then the system will request that link.
<p>3. The system will try to pull the origin stream for 2 hours approximately, making requests approximately every 3 seconds.</p>
   1. If one of the links works, the timer is reset to zero, transcoding begins.
   2. Otherwise the stream stops permanently. To resume it, you will have to activate it manually or via API.

## Stream availability

<p>A live stream typically requires a short initialization period before playback becomes available. Our system initializes all required services within ~2â€“5 seconds, from receiving a live stream at the ingester to publishing segments on the CDN.</p>

<Info>
  Stream segments become available in the CDN (and player) within ~2â€“5 seconds after the `type: stream (live=true)` webhook is issued.
</Info>

<p>Workflow when starting a stream on server:</p>

- Accept and check the stream on the ingester
- Initialize the stream
- **Send a webhook**
- Start the transcoding process
- Publish the first segment to the CDN
- **Playback available** â€“ here your player can start downloading video segments

## Players behavior

<p>Please note that the manifest and fragments will be available again at the time indicated above. Consider your player configuration for automatic playback of restored live stream. Some players resume playback with a large delay automatically. But if you update them manually, the video will appear instantly.</p>

<p>Use built-in retry knobs and an error handler that re-loads the manifest when it comes back.</p>

<p>For example:</p>

```text
  hls.js:
  manifestLoadingMaxRetry: 10,
  manifestLoadingRetryDelay: 1000,

  dash.js:
  retryAttempts: { manifest: 100, media: 10, lowLatency: 10 },
  retryIntervals: { manifest: 1_000, media: 1_000, lowLatency: 1_000 },
  rebufferToLive: true,
```

## Configure a stream for PUSH ingest

<p>Set `pull: false` (or omit it â€” `false` is the default) to configure a stream for PUSH mode. The response immediately contains all ingest URLs. Pass the appropriate URL to your encoder.</p>

<Tabs>
  <Tab title="Python SDK">
```python
import os
from gcore import Gcore

stream_id = int(os.environ["STREAM_ID"])

client = Gcore()
stream = client.streaming.streams.update(
    stream_id,
    stream={"pull": False},
)
print(f"Primary RTMP:  {stream.push_url}")
print(f"Backup RTMP:   {stream.backup_push_url}")
print(f"Primary SRT:   {stream.push_url_srt}")
print(f"Backup SRT:    {stream.backup_push_url_srt}")

```
  </Tab>
  <Tab title="Go SDK">
```go
package main

import (
	"context"
	"fmt"
	"os"
	"strconv"

	gcore "github.com/G-Core/gcore-go"
	"github.com/G-Core/gcore-go/packages/param"
	"github.com/G-Core/gcore-go/streaming"
)

func main() {
	streamID, _ := strconv.ParseInt(os.Getenv("STREAM_ID"), 10, 64)

	ctx := context.Background()
	client := gcore.NewClient()

	// The Go SDK requires Name in every Update call.
	// Read the current name first to avoid overwriting it.
	existing, err := client.Streaming.Streams.Get(ctx, streamID)
	if err != nil {
		panic(err)
	}

	stream, err := client.Streaming.Streams.Update(ctx, streamID, streaming.StreamUpdateParams{
		Stream: streaming.StreamUpdateParamsStream{
			Name: existing.Name,
			Pull: param.NewOpt(false),
		},
	})
	if err != nil {
		panic(err)
	}
	fmt.Printf("Primary RTMP: %s\n", stream.PushURL)
	fmt.Printf("Backup RTMP:  %s\n", stream.BackupPushURL)
	fmt.Printf("Primary SRT:  %s\n", stream.PushURLSrt)
	fmt.Printf("Backup SRT:   %s\n", stream.BackupPushURLSrt)
	fmt.Printf("WebRTC WHIP:  %s\n", stream.PushURLWhip)
}
```

## Reactivate a stopped PULL stream

<p>After the 2-hour retry period expires without a successful connection, the platform sets `active` to `false`. Send a PATCH request with `active: true` to resume pulling.</p>

<Tabs>
  <Tab title="Python SDK">
```python
import os
from gcore import Gcore

stream_id = int(os.environ["STREAM_ID"])

client = Gcore()
stream = client.streaming.streams.update(
    stream_id,
    stream={"active": True},
)
print(f"Stream {stream.id}: active={stream.active}")
```
  </Tab>
  <Tab title="Go SDK">
```go
package main

import (
	"context"
	"fmt"
	"os"
	"strconv"

	gcore "github.com/G-Core/gcore-go"
	"github.com/G-Core/gcore-go/packages/param"
	"github.com/G-Core/gcore-go/streaming"
)

func main() {
	streamID, _ := strconv.ParseInt(os.Getenv("STREAM_ID"), 10, 64)

	ctx := context.Background()
	client := gcore.NewClient()

	// The Go SDK requires Name in every Update call.
	// Read the current name first to avoid overwriting it.
	existing, err := client.Streaming.Streams.Get(ctx, streamID)
	if err != nil {
		panic(err)
	}

	stream, err := client.Streaming.Streams.Update(ctx, streamID, streaming.StreamUpdateParams{
		Stream: streaming.StreamUpdateParamsStream{
			Name:   existing.Name,
			Active: param.NewOpt(true),
		},
	})
	if err != nil {
		panic(err)
	}
	fmt.Printf("Stream %d: active=%v\n", stream.ID, stream.Active)
}
```

```bash
     -H "Authorization: APIKey $GCORE_API_KEY" \
     -H "Content-Type: application/json" \
     -d '{"active": true}'
```

## Reset the PUSH Token

<p>Send <code>POST&nbsp;/streaming/streams/{"{stream_id}"}/reset_push_token</code>. The response contains the full updated stream object with the new token embedded in all push URLs.</p>

<p>The reset takes effect immediately. The old token is invalidated â€” any encoder still using the old ingest URL will be rejected. Active primary and backup ingest connections may be terminated by the platform. Plan token rotation during a maintenance window, or be prepared to restart the encoder with the new ingest URL immediately after the reset.</p>

```bash
curl -X POST "https://api.gcore.com/streaming/streams/$STREAM_ID/reset_push_token" \
     -H "Authorization: APIKey $GCORE_API_KEY"
```

<p>The response contains the full updated stream object. Extract the new ingest URLs from `push_url`, `backup_push_url`, `push_url_srt`, `backup_push_url_srt`, and `push_url_whip`.</p>
