## PUSH ingest

<p>In PUSH mode, an encoder, broadcast software, app, or automation agent initiates the connection and sends the live stream to Gcore. The encoder is configured with a target ingest URL and stream key; Gcore Streaming listens for incoming connections and authenticates them using the push token embedded in the URL.</p>

```text
PUSH:
Encoder (FFmpeg/OBS/etc.)  --->  Gcore ingest  --->  Transcoding + CDN  --->  HTML player
```

<p>The push token is the secret part of the ingest URL. Only one push token exists for a stream at a time; anyone with a valid push URL can publish to that stream. The [Reset&nbsp;push&nbsp;token](/api-reference/streaming/streams/reset-live-stream-push-token) API endpoint rotates the token programmatically; the **Reset the PUSH token** section below covers the portal procedure.</p>

### Supported protocols

<p>Protocols supported for PUSH ingest:</p>

- RTMP/RTMPS -- Widely supported in encoders and streaming software.
- SRT -- Secure and reliable, recommended for contribution over the Internet.
- WebRTC WHIP -- Low-latency contribution from browsers or apps.

<Info>
  Only one ingest protocol type can be used for a live stream at a time -- pushing RTMP and then attempting WebRTC WHIP simultaneously causes the transcoding process to fail.

  Example of server response after sending a second stream:

  ```text
  [out#0/flv @ 0x600003934000] Error muxing a packet
  [out#0/flv @ 0x600003934000] Task finished with error code: -32 (Broken pipe)
  [out#0/flv @ 0x600003934000] Terminating thread with return code -32 (Broken pipe)
  [out#0/flv @ 0x600003934000] Error writing trailer: Broken pipe
  [out#0/flv @ 0x600003934000] Error closing file: Broken pipe
  ```
</Info>

<p>To configure an encoder for PUSH ingest:</p>

1. Select one protocol (RTMP, SRT, or WebRTC WHIP).
2. Configure the encoder with the ingest URL and stream key from the stream settings.
3. Verify that the network/firewall allows outbound TCP (for RTMP/RTMPS) and UDP (for SRT, WebRTC).

<Info>
  The origin stream must meet the [codec&nbsp;requirements](/streaming/live-streams-and-videos-protocols-and-codecs/input-parameters-and-codecs) for supported protocols, video and audio codecs, GOP structure, and bitrate. Streams that deviate from the documented specifications may be rejected by the ingest server or cause unstable transcoding.
</Info>

### PUSH link formats

<p>PUSH ingest URLs are returned in the stream object and are also available in the control panel. Use the exact URL for the protocol selected in the stream settings:</p>

| Protocol | Field | Format |
| --- | --- | --- |
| RTMP/RTMPS | `push_url`, `backup_push_url` | `rtmp://rtmp.domain.com/in/{stream_id}?{push_token}` |
| RTMP/RTMPS (legacy cameras) | `push_url`, `backup_push_url` | `rtmp://rtmp.domain.com/in/{stream_id}/{push_token}` |
| SRT | `push_url_srt`, `backup_push_url_srt` | `srt://srt.domain.com:5001?streamid={stream_id}#{push_token}` |
| WebRTC WHIP | `push_url_whip` | `https://whip.domain.com/{stream_id}_{push_token}/whip` |

<p>Examples:</p>

```text
rtmp://rtmp.domain.com/in/1234567?aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
srt://srt.domain.com:5001?streamid=1234567#aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
https://whip.domain.com/1234567_aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa/whip
```

<p>Legacy RTMP cameras that don't support query strings in the URI accept an alternative path-based format, where the push token is a path segment instead of a query parameter:</p>

```text
rtmp://rtmp.domain.com/in/1234567/aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
```

<p>For enterprise projects, the ingest URL format can be adapted to existing business or encoder requirements. If the current workflow uses this style:</p>

```text
rtmp(s)://<ip:port>/app/<uuid>
```

<p>Gcore can provide a compatible format:</p>

```text
rtmp://vp-push-anx1.gvideo.co/app/76ac4a8b-5ff3-9028-2a4b-a31a23e5900a
```

<p>Contact an account manager or [support](https://gcore.com/contact-us) to request a custom ingest URL format.</p>

### Primary and backup ingest points

<p>Gcore Streaming provides a failover mechanism for RTMP and SRT origin streams: both primary and backup streams can be pushed simultaneously. Primary and backup streams use their respective dedicated ingest URLs -- do not send both encoder outputs to the same push URL.</p>

<p>Use for RTMP/S:</p>

- `push_url` -- as primary
- `backup_push_url` -- as backup

<p>Use for SRT:</p>

- `push_url_srt` -- as primary
- `backup_push_url_srt` -- as backup

<p>**PUSH fallback algorithm:**</p>

1. The primary stream is active. The primary always takes priority over the backup stream.
2. When the primary stream fails and is unavailable for more than 3 seconds, the fallback process begins (the backup stream must be available and online):
   1. A new transcoding process starts for the backup stream.
   2. End-viewers will be without stream data for approximately 15 seconds.
3. When the primary stream is restored, a timer starts counting how long the primary has been active. The primary must remain available for at least 60 consecutive seconds before Gcore Streaming transitions back to it:
   1. A new transcoding process starts for the primary stream.
   2. End-viewers will be without stream data for approximately 15 seconds.

- Europe Luxembourg, The Netherlands
- US Ashburn, Miami
- Singapore (location under development)

### PUSH ingest limits

<p>The ingest server enforces the following security rules:</p>

1. After a connection is established with a valid stream key, the server registers it as active. While this session remains active, any subsequent connection attempts using the same stream key will be rejected. The ingest protocol does not provide error codes for this case, so rejections occur silently. To check whether a stream is currently active, use the UI or API.
2. The server enforces a connection rate limit: if too many reconnection attempts are made in a short period, new attempts will be denied. This is relevant when an encoder restarts repeatedly after a failure. To avoid triggering the limiter, allow at least 10 seconds between connection attempts.

<Info>
  Each stream key accepts one active connection using one ingest protocol at a time. Additional simultaneous connections or protocols on the same input are rejected -- pushing primary RTMP and backup RTMP to the same single `push_url` simultaneously causes the transcoding process to fail.
</Info>

### Reset the PUSH token

<p>Reset the push token if it was exposed, shared with the wrong encoder, or must be rotated as part of a security process. After a reset:</p>

- The old token is immediately invalidated.
- The new token is returned by the API and becomes available in the control panel.
- Encoders that still use the old URL will be rejected.
- Gcore Streaming tries to terminate active primary and backup ingest connections automatically.

<Info>
  Token reset affects active broadcasting. Plan token rotation during a maintenance window or be ready to restart the encoder with the new ingest URL.
</Info>

<p>To reset the push token, open the stream settings, locate **URLs for encoder**, and click the reset icon next to the **Stream Key** field. The REST API tab provides examples for automated token rotation.</p>

## PULL

<p>In PULL mode, Gcore connects to a public origin URL and fetches the stream. Use PULL when the stream source is accessible over the internet and the encoder cannot initiate an outbound connection to Gcore.</p>

```text
PULL:
Public origin URL  <---  Gcore ingest  --->  Transcoding + CDN  --->  HTML player
```

### Failover with multiple source URIs

<p>The **URL** field accepts one or more source addresses. Multiple addresses are separated by a space, providing an additional backup plan.</p>

<p>Single source:</p>

```text
rtmp://encoder.example.com/live/stream123
```

<p>Multiple sources with fallback:</p>

```text
rtmp://encoder1.example.com/live/stream123 rtmp://encoder2.example.com/live/stream123_backup srt://encoder3.example.com:9000?mode=caller&latency=1000000&streamid=stream123
```

<p>In the Customer Portal, open a live stream's settings, enable **PULL**, and paste the origin URL (or multiple URLs separated by a space) into the **URL** field.</p>

<p>**PULL fallback algorithm:**</p>

1. Stream #1 is active.
2. If the first source is unavailable for more than approximately 3 seconds, Gcore Streaming switches to the next address in the **URL** field:
   1. A new transcoding for the backup stream is started.
   2. End viewers will be without stream data for approximately 15 seconds.
   3. If the second source also fails, Gcore Streaming repeats this process for the next address using a round-robin algorithm. If only one address is configured, Gcore Streaming retries that address.
3. Gcore Streaming retries for approximately 2 hours, making requests every 3 seconds.
   1. If a link becomes available, the timer resets and transcoding begins.
   2. If no link responds within 2 hours, the stream stops. Resume by reactivating the stream manually or via API.

<p>For geo-distributed PULL ingest, contact [support](https://gcore.com/contact-us) or an account manager. Selecting an ingest location close to the origin minimizes latency between Gcore and the source.</p>

## Configure a stream for PUSH ingest

<p>Set `pull: false` (or omit it -- `false` is the default) to configure a stream for PUSH mode. The response immediately contains all ingest URLs. Pass the appropriate URL to the encoder.</p>

<Tabs>
  <Tab title="Python SDK">
```python
import os
from gcore import Gcore

stream_id = int(os.environ["STREAM_ID"])

client = Gcore()
stream = client.streaming.streams.update(
    stream_id,
    stream={"pull": False},
)
print(f"Primary RTMP:  {stream.push_url}")
print(f"Backup RTMP:   {stream.backup_push_url}")
print(f"Primary SRT:   {stream.push_url_srt}")
print(f"Backup SRT:    {stream.backup_push_url_srt}")
print(f"WebRTC WHIP:   {stream.push_url_whip}")
```
  </Tab>
  <Tab title="Go SDK">
```go
package main

import (
	"context"
	"fmt"
	"os"
	"strconv"

	gcore "github.com/G-Core/gcore-go"
	"github.com/G-Core/gcore-go/packages/param"
	"github.com/G-Core/gcore-go/streaming"
)

func main() {
	streamID, _ := strconv.ParseInt(os.Getenv("STREAM_ID"), 10, 64)

	ctx := context.Background()
	client := gcore.NewClient()

	// The Go SDK requires Name in every Update call.
	// Read the current name first to avoid overwriting it.
	existing, err := client.Streaming.Streams.Get(ctx, streamID)
	if err != nil {
		panic(err)
	}

	stream, err := client.Streaming.Streams.Update(ctx, streamID, streaming.StreamUpdateParams{
		Stream: streaming.StreamUpdateParamsStream{
			Name: existing.Name,
			Pull: param.NewOpt(false),
		},
	})
	if err != nil {
		panic(err)
	}
	fmt.Printf("Primary RTMP: %s\n", stream.PushURL)
	fmt.Printf("Backup RTMP:  %s\n", stream.BackupPushURL)
	fmt.Printf("Primary SRT:  %s\n", stream.PushURLSrt)
	fmt.Printf("Backup SRT:   %s\n", stream.BackupPushURLSrt)
	fmt.Printf("WebRTC WHIP:  %s\n", stream.PushURLWhip)
}
```

## Failover with multiple source URIs for PULL

<p>Set `pull: true` and provide one or more source URLs in the `uri` field, separated by spaces. Gcore Streaming cycles through URIs in round-robin order on failure. After 2 hours with no successful connection, the stream deactivates (`active` -> `false`); use the Reactivate section below to resume it.</p>

<Tabs>
  <Tab title="Python SDK">
```python
import os
from gcore import Gcore

stream_id = int(os.environ["STREAM_ID"])

client = Gcore()
stream = client.streaming.streams.update(
    stream_id,
    stream={
        "name": "My PULL stream",
        "pull": True,
        "uri": "rtmp://encoder1.example.com/live/stream123 rtmp://encoder2.example.com/live/stream123_backup",
    },
)
print(f"Stream {stream.id}: pull={stream.pull}, uri={stream.uri}")
```

## Reset the PUSH token

<p>Send <code>POST&nbsp;/streaming/streams/{"{stream_id}"}/reset_push_token</code>. The response contains the full updated stream object with the new token embedded in all push URLs.</p>

<p>The reset takes effect immediately. The old token is invalidated -- any encoder still using the old ingest URL will be rejected. Gcore Streaming tries to terminate active primary and backup ingest connections. Plan token rotation during a maintenance window, or be prepared to restart the encoder with the new ingest URL immediately after the reset.</p>

```bash
curl -X POST "https://api.gcore.com/streaming/streams/$STREAM_ID/reset_push_token" \
     -H "Authorization: APIKey $GCORE_API_KEY"
```

<p>The response contains the full updated stream object. Extract the new ingest URLs from `push_url`, `backup_push_url`, `push_url_srt`, `backup_push_url_srt`, and `push_url_whip`.</p>
