SRT (Secure Reliable Transport) is an open-source, UDP-based protocol for live stream ingest. It provides low-latency delivery over unpredictable networks and supports H.265/HEVC in addition to H.264.

## SRT requirements

SRT ingest uses port `5001` (UDP). Configure the encoder with:

- Video codec and bitrate — [input&nbsp;parameters](/streaming/live-streams-and-videos-protocols-and-codecs/input-parameters-and-codecs)
- SRT latency: configure based on network conditions — [Configure&nbsp;SRT&nbsp;latency](#configure-srt-latency)
- Keyframe interval: `1sec`
- CPU usage preset: `veryfast`
- Profile: `baseline`
- Low-latency encoder tuning: disable lookahead and B-frames — [Zerolatency&nbsp;encoder&nbsp;tuning](#zerolatency-encoder-tuning)

For differences between SRT and RTMP — [RTMP&nbsp;vs&nbsp;SRT](/streaming/live-streaming/protocols/rtmp-srt).

<Info>
When the SRT encoder connects, live transcoding reads the source FPS once from the incoming stream metadata at the beginning of the session. That FPS value is not re-read later and is not changed dynamically during transcoding. Gcore does not upscale a 10-12 fps source to 50 or 60 fps. If the source FPS was already degraded when the SRT session started, reconnect the stream from the encoder side after fixing the source settings.
</Info>


## SRT PUSH

In PUSH mode, the encoder establishes the connection and sends the stream to a Gcore ingest point. This mode works with software encoders (OBS, FFmpeg) and hardware encoders (Elemental, Haivision).

### Obtain the server URLs

There are two ways to obtain the SRT server URLs: via the [Gcore Customer Portal](https://portal.gcore.com) or via the API.

#### Via UI

1. In the Customer Portal, navigate to **Streaming** \> [**Live&nbsp;Streaming**](https://portal.gcore.com/streaming/streaming/list).

<Frame>
  ![Live streaming list with stream names and connection types](/images/docs/streaming/live-streaming/protocols/srt/srt-live-stream-list.png)

2. Click the stream. The **Live stream settings** page opens.

<Frame>
  ![Live stream settings page with Ingest type and Enable live stream toggle](/images/docs/streaming/live-streaming/protocols/srt/srt-live-stream-settings.png)
</Frame>

3. Set the **Ingest type** to **Push**.
4. In the **URLs for encoder** section, select **SRT**.
5. Copy the URL from the **Push URL SRT** field.

<Frame>

The ingest URL has the format `srt://vp-push-ed2-srt.gvideo.co:5001?streamid=12345#aaabbbcccddd`:
- protocol `srt://`
- server location — `vp-push-ed2-srt` is in Europe
- port `:5001`
- stream ID and key `?streamid=12345#aaabbbcccddd`

Backup ingest URLs and region selection: [Ingest&nbsp;&amp;&nbsp;Backup](/streaming/live-streaming/primary-backup).

### Configure SRT latency

The SRT `latency` parameter defines how long SRT buffers data to recover from packet loss and jitter. A shorter latency reduces end-to-end delay but exposes more network issues; a longer latency increases stability by masking errors.

Set the latency value manually — do not rely on encoder defaults. Recommended ranges by network conditions:

| Network conditions | Typical RTT (ms) | Jitter/Loss | Recommended latency (ms) |
|---|---|---|---|
| Same datacenter | &lt;20 | Very low | 150–400 |
| Same country, stable uplink | 20–100 | Low (&lt;0.5% loss) | 600–1000 |
| Cross-region, higher variability | 100–300 | Moderate (&lt;1%) | 1000–2000 |
| Unstable or mobile internet | &gt;300 | High (&gt;1% bursts) | 2000–2500 |

Keep latency below 3000 ms — Gcore ingest has a three-second inactivity timeout.

The latency unit depends on the encoder: FFmpeg requires microseconds (`&latency=2500000`), while OBS, GStreamer, and most other encoders use milliseconds (`&latency=2500`). Full reference: [FFmpeg&nbsp;protocol&nbsp;reference](https://ffmpeg.org//ffmpeg-protocols.html#srt).

#### Zerolatency encoder tuning

Lookahead and B-frames buffer and reorder frames inside the encoder before they reach the SRT sender. This encoder-side delay can cause packets to arrive outside the configured SRT latency window, resulting in late-packet drops and broken ingest.

For live SRT ingest, disable lookahead and B-frames:

- `-tune zerolatency` — disables lookahead and frame reordering
- `rc-lookahead=0` — disables the lookahead cache
- `bframes=0` — disables B-frames
- `scenecut=0` — disables lookahead-based scene detection

With `zerolatency` tuning, the buffer collapses to near zero:

#### Verify with SRT statistics

Enable SRT stats on the sender and monitor:

- RTT and jitter: round-trip time and variability. Drives latency sizing.
- Loss and retransmissions: `pkt*Loss`, `pkt*Retrans`, `pkt*Drop`. Rising values — increase latency or reduce bitrate.
- Buffer occupancy: send/receive buffer fill vs negotiated latency; approaching 0 under loss means the latency window is too small.

Full reference: [SRT&nbsp;statistics&nbsp;documentation](https://github.com/Haivision/srt/blob/master/docs/API/statistics.md).

A healthy send with a 2500 ms window and zero packet loss:

```json
{
    "bytes": 137032683360,
    "bytesDropped": 0,
    "bytesLost": 0,
    "mbitRate": 10.68,
    "packets": 100759326,
    "packetsBelated": 0,
    "packetsDropped": 0,
    "packetsFilterExtra": 0,
    "packetsFilterLoss": 0,
    "packetsFilterSupply": 0,
    "packetsLost": 0,
    "packetsRetransmitted": 0
}
```

### Protect SRT ingest with a passphrase

For SRT PUSH streams, a passphrase can be required on the ingest connection. When `srt_passphrase` is set for a live stream, the encoder must send the same passphrase when connecting to the SRT ingest URL. The incoming MPEG-TS stream is then AES-encrypted by SRT between the sender and the Gcore ingester.

This protects the ingest path from the encoder to Gcore. It does not encrypt playback URLs and does not replace viewer-side access protection.

Passphrase requirements:
- 10 to 80 characters
- ASCII letters, digits, and punctuation only
- No spaces or non-ASCII characters

Set the passphrase via the API:

```http
PATCH /streaming/streams/{stream_id}
```

```json
{
  "stream": {
    "srt_passphrase": "01234567890"
  }
}
```

To disable passphrase protection, update `srt_passphrase` to `null`.

Send the same passphrase from the encoder. In FFmpeg, pass it as a separate output option:

```sh
ffmpeg -hide_banner -re -i file.mp4 -c copy -passphrase 01234567890 -f mpegts \
  "srt://vp-push-ed2-srt.gvideo.co:5001?streamid=123#abc719"
```

Or add it to the SRT URL:

```sh
ffmpeg -hide_banner -re -i file.mp4 -c copy -f mpegts \
  "srt://vp-push-ed2-srt.gvideo.co:5001?streamid=123#abc719&passphrase=01234567890"
```

If the passphrase in the stream settings and the passphrase sent by the encoder do not match, the SRT ingest connection is rejected.

### Encoder examples

Each encoder below uses the zerolatency preset and explicit SRT latency. Latency units vary: FFmpeg requires microseconds, GStreamer and OBS use milliseconds.

#### FFmpeg SRT

This FFmpeg command generates a live 1080p/30fps test video with sine-wave audio, encodes it as MPEG-TS, and sends it over SRT in caller mode with a 2.5-second latency window.

```sh
ffmpeg -re \
  -f lavfi -i "testsrc=size=1920x1080:rate=30" \
  -f lavfi -i "sine=frequency=1000:sample_rate=48000" \
  -c:v libx264 -preset veryfast -tune zerolatency -x264-params "rc-lookahead=0:bframes=0:scenecut=0" \
  -g 30 -keyint_min 30 -pix_fmt yuv420p -b:v 3000k \
  -c:a aac -b:a 128k \
  -f mpegts \
  "srt://vp-push-ed2-srt.gvideo.co:5001?mode=caller&latency=2500000&streamid=123#abc719"
```

FFmpeg key points:
- `-tune zerolatency` — disables lookahead and frame reordering
- `-g 30 -keyint_min 30` — keeps GOP strictly predictable
- `-pix_fmt yuv420p` — forces common YUV planar pixel format for broad H.264 encoder compatibility
- `mode=caller` — PUSH mode from FFmpeg to ingest
- `&latency=2500000` — 2.5 sec SRT buffering (µs, microseconds in FFmpeg)
- `&streamid=id#key` — stream ID taken from the portal or API, ID and key separated by `#`

Full reference: [FFmpeg](/streaming/live-streaming/broadcasting-software/ffmpeg).

#### GStreamer SRT

This GStreamer pipeline generates a live 1080p/30fps test video with sine-wave audio, encodes it as MPEG-TS, and sends it over SRT in caller mode with a 2.5-second latency window.

```sh
gst-launch-1.0 -v \
    videotestsrc is-live=true pattern=smpte ! \
        video/x-raw,format=I420,width=1920,height=1080,framerate=30/1 ! \
        x264enc tune=zerolatency bitrate=3000 speed-preset=veryfast key-int-max=30 bframes=0 ! \
        h264parse config-interval=1 ! queue ! mux. \
    audiotestsrc is-live=true wave=sine ! \
        audio/x-raw,channels=2,rate=48000 ! \
        avenc_aac bitrate=128000 ! queue ! mux. \
    mpegtsmux name=mux ! \
    srtsink uri="srt://vp-push-ed2-srt.gvideo.co:5001" \
            mode=caller latency=2500 \
            streamid="123#abc719"
```

Full reference: [GStreamer](/streaming/live-streaming/broadcasting-software/gstreamer).

#### OBS SRT

1. In **Settings** > **Stream**, select **Custom** and enter the full SRT URL in **Server**:
```
srt://vp-push-ed2-srt.gvideo.co:5001?mode=caller&latency=2000000&streamid=123#abc719
```
2. Use x264 with low-latency settings to prevent encoder buffering that can exceed the SRT latency window.
3. Set H.264 parameters via **Advanced Encoder Options** in OBS:
   - Keyframe interval: 1s
   - CPU Usage Preset: veryfast
   - Profile: baseline
   - Tune: zerolatency
   - x264 Options: `rc-lookahead=0`

Full reference: [OBS](/streaming/live-streaming/broadcasting-software/obs).

#### vMix SRT

1. Open **Settings** > **Outputs/NDI/SRT/SRT** and create an output with:
   - Destination: `srt://HOST:PORT`
   - Mode: Caller
   - Latency: 2000 ms (or appropriate value based on network conditions)
   - Stream ID: enter the value from the portal (`123#abc719` format)
2. Enable Low Latency / No B-frames in vMix by applying equivalent x264 settings:
   - Encoder Preset: veryfast
   - Tune: zero latency
   - Custom x264 Params: `rc-lookahead=0`

#### Other encoders

For other encoders, consult the encoder documentation to apply the equivalent low-latency tuning parameters.


## SRT PULL

In PULL mode, Gcore Video Streaming connects to an origin URL and retrieves the stream.

Source requirements:
- The source URL can use RTMP, SRT, or HLS (M3U8) format.
- The URL of the stream to pull from must be publicly available and return data for all requests.
- To restrict access with an allowlist, contact support for the current list of Gcore networks.

### Setting up PULL stream

There are two ways to set up a pull stream: via the Gcore Customer Portal or via the API.

#### Via UI

1. In the Customer Portal, navigate to **Streaming** \> [**Live&nbsp;Streaming**](https://portal.gcore.com/streaming/streaming/list).

<Frame>
  ![Live streaming list with stream names and connection types](/images/docs/streaming/live-streaming/protocols/srt/srt-live-stream-list.png)
</Frame>

2. Click the live stream to configure for pull ingest. The **Live stream settings** page opens.

<Frame>
  ![Live stream settings page with Ingest type and Enable live stream toggle](/images/docs/streaming/live-streaming/protocols/srt/srt-live-stream-settings.png)
</Frame>

3. Set the **Ingest type** to **Pull**.
4. In the **URL** field, enter the source stream URL. The source can be an RTMP, SRT, or HLS (M3U8) URL.
5. Click the **Save changes** button in the top right.

<Frame>
  ![Live stream settings page in Pull mode with the URL field showing an SRT source URL](/images/docs/streaming/live-streaming/protocols/srt/srt-pull-stream-settings.png)
</Frame>

#### Via API

Pull ingest can also be configured via the Gcore API.

```http
PATCH /streaming/streams/{stream_id}
```

```json
{
  "stream": {
    "pull": true,
    "uri": "srt://example.com/path/to/stream",
    ...
  }
}
```

Full API reference: [Change&nbsp;live&nbsp;stream](/api-reference/streaming/streams/change-live-stream).


## Ingest limits

Gcore applies two constraints to all live stream ingest connections.

<Info>
Only one ingest protocol type can be used for a live stream at a time.
Pushing SRT and another protocol (e.g., RTMP) to the same stream at once will cause transcoding to fail.
</Info>

The ingester timeout is 3 seconds (3000&nbsp;ms). If no data arrives within this period, the connection is discarded as inactive and the encoder must reconnect.


## SRT troubleshooting

Packet loss on the ingest path can cause picture corruption, dropped frames, or buffering.

Check SRT statistics for packet loss and retransmissions. If loss is present, adjust latency according to the recommendations in [Configure&nbsp;SRT&nbsp;latency](#configure-srt-latency) and reduce bitrate if the available uplink bandwidth is insufficient.
