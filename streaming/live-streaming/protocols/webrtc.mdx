<p>HLS and MPEG-DASH distribute video to large audiences with adaptive bitrate streaming, but they require an ingest format that browsers do not support natively. WebRTC operates in any browser without additional software, yet does not support ABR distribution on its own.</p>

<p>Gcore [Video&nbsp;Streaming](https://gcore.com/streaming-platform) combines both: WebRTC HTTP Ingest Protocol (WHIP) for low-latency browser ingest, with automatic transcoding to HLS/DASH for CDN delivery.</p>

<Frame>![A diagram depicting WebRTC converting to LL-HLS/DASH](/images/docs/streaming/live-streaming/protocols/webrtc/diagram-whip-hls-protocols-supported.png)</Frame>

## Architecture

<p>A dedicated WebRTC WHIP server handles both signaling and video data reception. Signaling is the negotiation between WebRTC endpoints required to establish a session. WHIP is an open specification for a simple signaling protocol that initiates WebRTC sessions in an outgoing direction.</p>

<p>Gcore runs WHIP servers in each region to minimize the route from the presenter's device to the ingest point. Once ingested, the stream enters the same transcoding and CDN pipeline as RTMP and SRT streams.</p>

### LL-HLS and LL-DASH outputs

<p>Streams sent via WebRTC are transcoded in the same way as other streams received via RTMP and SRT.</p>

<p>Output protocols:</p>

  * **MPEG-DASH**: ±2–4 seconds latency to a viewer with ABR.
  * **LL-HLS**: ±3–4 seconds latency to a viewer with ABR.
  * **HLS MPEG-TS**: legacy with [non-low-latency](/streaming/live-streaming/how-low-latency-streaming-works#switch-to-legacy-hls-modes) (±10 seconds latency) with ABR.

<p>For WebRTC mode, Gcore uses constant transcoding at the original target resolution. When a viewer's WebRTC client reduces the master stream resolution — say, to 360p — due to network congestion or CPU load, the transcoder continues to transcode to the original target resolution, 1080p with ABR.</p>

<p>When network or device conditions improve, the quality returns to the original level.</p>

## Stream from a custom application

### Supported WHIP clients

<p>WHIP is an open standard, so streams can be published with the Gcore browser client or any compatible WHIP encoder.</p>

  * Gcore JS WebRTC WHIP client — [GitHub&nbsp;repository](https://github.com/G-Core/gcore-webrtc-sdk-js) with source code, usage docs, and integration guides.
  * Portal webcam publisher — uses the Gcore JS WHIP client; started via **Start WebRTC + webcam**.
  * [OBS](https://obsproject.com/) (Open Broadcaster Software)
  * [@eyevinn/whip-web-client](https://web.whip.eyevinn.technology/)
  * [whip-go](https://github.com/ggarber/whip-go)
  * Larix Broadcaster (iOS and Android; WebRTC based on Pion, SDK available)

### Encoding requirements

<p>The stream must include at least one video track (H.264) and one audio track (OPUS).</p>

<Tabs>
  <Tab title="OBS">
    <p>Apply these video encoding parameters in OBS:</p>

      * Codec H.264 with no B-frames and fast encoding:

        * **Encoder**: x264, or any H.264 encoder
        * **CPU usage**: very fast
        * **Keyframe interval**: 1 sec
        * **Profile**: baseline
        * **Tune**: zero latency
        * **x264 options**: bframes=0 scenecut=0
      * Bitrate: the lower the bitrate, the faster the data is transmitted. A typical range for online training or presenter broadcasts is 1–2 Mbps.

    <Frame>![Example of listed OBS settings](/images/docs/streaming/live-streaming/protocols/webrtc/example-obs-settings.png)</Frame>
  </Tab>
  <Tab title="Custom WHIP client">
    <p>Apply these parameters for any WHIP-compatible encoder or custom implementation:</p>

      * **Video codec**: H.264, no B-frames, fast profile (baseline, zero-latency tune)
      * **Audio codec**: OPUS
      * **Keyframe interval**: 1 second
      * **Bitrate**: 1–2 Mbps is typical for presenter streams
  </Tab>
</Tabs>

### Start with the Gcore WHIP library

<p>The Gcore WebRTC WHIP client publishes camera and microphone streams from a browser to a WHIP endpoint. It handles signaling, camera/mic access, and event monitoring. The latest version is on the [releases](https://github.com/G-Core/gcore-webrtc-sdk-js/releases) page; for version 0.89.14, load `https://rtckit.gvideo.io/0.89.14/index.esm.js`.</p>

3. In the [WHIP&nbsp;demo&nbsp;app](https://stackblitz.com/edit/stackblitz-starters-j2r9ar?file=index.html), paste the WHIP URL into the `WHIP_ENDPOINT const`.

4. Click the **Start** button. The stream will start.

<p>The [gcorevideo/rtckit](https://github.com/G-Core/gcore-webrtc-sdk-js/blob/main/packages/rtckit/docs/api/rtckit.md) repository contains the full technical reference on data types, interfaces, and methods.</p>

### Stream from custom code

<p>Get access and data from the microphone and camera:</p>

```js
import { WebrtcStreaming } from 'https://rtckit.gvideo.io/0.89.14/index.esm.js';
const WHIP_ENDPOINT = '{push_url_whip}';
const webrtc = new WebrtcStreaming(WHIP_ENDPOINT, {...});
```

<p>Send a local stream to the WHIP server:</p>

```js
webrtc.openSourceStream({
 audio: mic,
 video: cam,
 resolution: 1080,
})
```

<p>If a user stops streaming by closing the browser tab or navigating away, the session terminates. When the user resumes streaming from any browser, the ingester picks up the stream with a brief delay before it becomes playable.</p>

<p>If a user tries to stream to the same endpoint where another user is already streaming, the former will get an error message from the media server. The current stream will remain uninterrupted.</p>

### Play HLS or DASH

<p>After the stream starts from the frontend, transcoding begins. Within ±2–7 seconds, the HLS and MPEG-DASH versions are ready for viewing.</p>

<p>The stream is viewable via the built-in web player or direct manifest links. Use the `iframe_url`, `hls_cmaf_url`, `hls_mpegts_url`, and `dash_url` fields from the stream response. The full response structure is shown in the **Get embed links** section of the REST API tab.</p>

<p>Link templates (replace with stream-specific values):</p>

  * Web player: https://player.gvideo.co/streams/102748_1965207
  * LL-HLS manifest: https://102748.gvideo.io/cmaf/102748_1965207/master.m3u8
  * DASH manifest: https://102748.gvideo.io/cmaf/102748_1965207/index.mpd

### Deactivate finished stream

<p>Close the stream from the browser with:</p>

```js
webrtc.close()
```

## Troubleshooting

### Cannot start publishing

<p>**NetworkError** ([NetworkError&nbsp;class](https://github.com/G-Core/gcore-webrtc-sdk-js/blob/main/packages/rtckit/docs/api/rtckit.networkerror.md)): The ingestion service is unavailable or unreachable from the client's network. The application should render itself unavailable and report the error to Gcore support. The app should not retry — retry logic is already implemented in the SDK.</p>

<p>Some SDK methods throw browser-native exceptions when device access fails. [WebrtcStreaming.openSourceStream](https://github.com/G-Core/gcore-webrtc-sdk-js/blob/main/packages/rtckit/docs/api/rtckit.webrtcstreaming.opensourcestream.md) and the methods of [MediaDevicesHelper](https://github.com/G-Core/gcore-webrtc-sdk-js/blob/main/packages/rtckit/docs/api/rtckit.mediadeviceshelper.md) throw [getUserMedia&#8209;originated&nbsp;exceptions](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia#exceptions). Handle these in the application accordingly.</p>

<p>Additional error types are documented in the [SDK&nbsp;docs](https://github.com/G-Core/gcore-webrtc-sdk-js/blob/main/packages/rtckit/docs/api/rtckit.md).</p>

### WHIP endpoint rejects the request

<p>**ServerRequestError** ([ServerRequestError&nbsp;class](https://github.com/G-Core/gcore-webrtc-sdk-js/blob/main/packages/rtckit/docs/api/rtckit.serverrequesterror.md)): The ingestion server returned an error. Identify it by inspecting the `status` and `detail` fields of the error object. WHIP publish requests can also return a non-200 HTTP response, so inspect the HTTP status code and the `X-Reason-Code` response header before retrying.</p>

<Accordion title="HTTP status codes and actions">
| HTTP status code | X-Reason-Code | Explanation | Action |
|------------------|---------------|-------------|--------|
| 400 | N/A | The client request is incorrect. This can happen when the WHIP client sends invalid request parameters. | Check the WHIP client configuration. If the response has no readable description, contact the Gcore support team. |
| 401 | 2001 | Stream does not exist. | Create a stream or use an existing stream's `push_url_whip`. |
| 403 | 2002 | Stream token is invalid. | Copy the current WHIP URL from the stream settings or reset the push token. |
| 403 | 2003 | Someone else is already streaming. | Stop the active publisher or wait about 30 seconds after an unclean disconnect before retrying. |
| 403 | 2004 | Stream is disabled. | Activate the stream in the API or Customer Portal and confirm that `active` is `true`. |
| 403 | 2005 | Client live streams limit reached. | Deactivate unused streams or ask the support team or account manager to increase the limit. |
| 403 | 2006 | Client status is not active. | Check the account status with the support team or account manager. |
| 500, 502, 503, 504, 5xx (infrequently) | N/A | Gcore infrastructure is experiencing pressure or outage. | Contact the Gcore support team. The app should render itself unavailable and must not retry the request. |

</Accordion>

### Connection times out

<p>**TimeoutError** ([TimeoutError&nbsp;class](https://github.com/G-Core/gcore-webrtc-sdk-js/blob/main/packages/rtckit/docs/api/rtckit.timeouterror.md)): An operation has timed out. A timeout can occur when the configured or automatically discovered ICE servers are unavailable or incorrectly configured.</p>

<p>ICE servers are configured explicitly via the iceServers [configuration&nbsp;option](https://github.com/G-Core/gcore-webrtc-sdk-js/blob/3e45d6e8beebcc7221625bd9e3b3b1749d9405ae/packages/rtckit/docs/api/rtckit.whipclientoptions.md). Without explicit configuration, they are fetched from Gcore's media server in the session initiation response. When fetched automatically, check what the WHIP server returns in the `Link` headers:</p>

<Frame>![Example data in Link headers](/images/docs/streaming/live-streaming/protocols/webrtc/link-headers.png)</Frame>

```
Link: ; rel="ice-server"
Link: ; rel="ice-server"; username="1730558739:0nu0id47meqbsyvpz743"; credential="IswwB19KAEWQujy3X/c4D9GjZj8="; credential-type="password"
Link: ...
```

<p>Also inspect the servers using <code>chrome://webrtc-internals</code> or an alternative tool:</p>

<Frame>![Example of servers check in Chrome WebRTC internals](/images/docs/streaming/live-streaming/protocols/webrtc/check-server-config.png)</Frame>

<p>Verify ICE connectivity with the [Trickle&nbsp;ICE](https://webrtc.github.io/samples/src/content/peerconnection/trickle-ice/) test app. Add a STUN or TURN server and confirm the results:</p>

  * A srvrflx candidate for STUN server
  * A relay candidate for a TURN server

<p>Missing these results indicates a STUN or TURN server misconfiguration or outage. Contact the [Gcore&nbsp;support&nbsp;team](mailto:support@gcore.com) and include the ICE connectivity check results to speed up resolution.</p>

### Camera or microphone disconnects

<p>Sometimes, users use external or plug-in cameras and microphones that can be disconnected at any time — a USB cable unplugged or AirPods returned to their case.</p>

<p>Track device disconnections programmatically to maintain uninterrupted broadcasting. Enable the `mediaDevicesAutoSwitch` option and subscribe to the event:</p>

  * Set `mediaDevicesAutoSwitch: true`
  * Subscribe to `WebrtcStreamingEvents`

<p>When a device disconnects, the browser switches to the next available camera or microphone automatically. The event payload identifies which device was disconnected and which one is now active, allowing the application to update the UI accordingly.</p>

<Frame>![A list of available devices with USB audio selected](/images/docs/streaming/live-streaming/protocols/webrtc/microphone-options.png)</Frame>

### Stream quality degrades

<p>If a stream constantly stops, is interrupted, or has poor quality, the issue is likely slow transmission from the presenter via WebRTC. WebRTC is sensitive to internet connection quality and may reduce or pause data transmission automatically when conditions deteriorate.</p>

<p>To diagnose:</p>

1. Use the **VideoResolutionChangeDetector** plugin to display a message when network conditions degrade on the presenter's device.

2. Open a new Chrome tab and navigate to <code>chrome://webrtc-internals</code> during the WebRTC call.

<p>Network congestion leads to packet loss, latency, and jitter. WebRTC uses Transport Wide Congestion Control (TWCC), described in the [TWCC&nbsp;overview](https://bloggeek.me/webrtcglossary/transport-cc/), to regulate data flow and optimize performance.</p>

<p>The **availableOutgoingBitrate** parameter indicates available outbound capacity, reported in bits per second over a one-second interval. Monitor it in **Stats graphs for candidate-pair**:</p>

<Frame>![AvailableOutgoingBitrate graph in Chrome WebRTC internals](/images/docs/streaming/live-streaming/protocols/webrtc/available-outgoing-bitrate-graph.png)</Frame>

<p>Also monitor these parameters from the **Stats graphs for outbound-rtp**:</p>

  * bytesSent_in_bits/s
  * targetBitrate
  * frameWidth
  * frameHeight
  * framesSent/s

<Frame>![frameWidth and frameHeight graphs in Chrome WebRTC internals](/images/docs/streaming/live-streaming/protocols/webrtc/frame-graphs.png)</Frame>

<p>When channel width becomes insufficient, video quality degrades. When packets are lost, the server sends NACK (Negative Acknowledgement) packets as described in the [NACK&nbsp;overview](https://bloggeek.me/webrtcglossary/nack/), increasing retransmissions and causing latency or frame gaps. Monitor this pattern:</p>

<Frame>![Example graphs in Chrome WebRTC internals tool](/images/docs/streaming/live-streaming/protocols/webrtc/sample-graphs-network-troubleshooting.png)</Frame>

<p>If the metrics indicate degraded network conditions, notify the user and consider these options:</p>

  * Use TCP as the delivery protocol instead of UDP.
  * Use the TURN server for delivery instead of sending directly to the media server.

## Create a stream

<p>Create a live stream and retrieve the WHIP ingest URL. Pass `push_url_whip` to a browser publisher or WHIP-compatible encoder to start sending media.</p>

<Tabs>
  <Tab title="Python SDK">
    ```python
    from gcore import Gcore

    client = Gcore()

    stream = client.streaming.streams.create(
        name="My WebRTC Stream",
        active=True,
    )
    print(f"Stream ID: {stream.id}")
    print(f"WHIP URL: {stream.push_url_whip}")
    ```
  </Tab>
  <Tab title="Go SDK">
    ```go
    package main

    import (
    	"context"
    	"fmt"

    	gcore "github.com/G-Core/gcore-go"
    	"github.com/G-Core/gcore-go/streaming"
    )

    func main() {
    	client := gcore.NewClient()
    	ctx := context.Background()

    	stream, err := client.Streaming.Streams.New(ctx, streaming.StreamNewParams{
    		Name:   "My WebRTC Stream",
    		Active: gcore.Bool(true),
    	})
    	if err != nil {
    		panic(err)
    	}
    	fmt.Printf("Stream ID: %d\n", stream.ID)
    	fmt.Printf("WHIP URL: %s\n", stream.PushURLWhip)
    }
    ```

## Deactivate a stream

<p>Set `active` to `false` to stop ingest processing. An inactive stream ignores PUSH attempts and cannot be pulled. To permanently remove a stream, call the [delete&nbsp;endpoint](/api-reference/streaming/streams/delete-stream) in the Streams API.</p>

<Tabs>
  <Tab title="Python SDK">
    ```python
    import os
    from gcore import Gcore

    client = Gcore()
    stream = client.streaming.streams.update(
        int(os.environ["STREAM_ID"]),
        stream={"active": False},
    )
    print(f"Active: {stream.active}")
    ```
  </Tab>
  <Tab title="Go SDK">
    ```go
    package main

    import (
    	"context"
    	"fmt"
    	"os"
    	"strconv"

    	gcore "github.com/G-Core/gcore-go"
    	"github.com/G-Core/gcore-go/streaming"
    )

    func main() {
    	client := gcore.NewClient()
    	ctx := context.Background()

    	streamID, _ := strconv.ParseInt(os.Getenv("STREAM_ID"), 10, 64)
    	stream, err := client.Streaming.Streams.Update(ctx, streamID, streaming.StreamUpdateParams{
    		Stream: streaming.StreamUpdateParamsStream{
    			Active: gcore.Bool(false),
    		},
    	})
    	if err != nil {
    		panic(err)
    	}
    	fmt.Printf("Active: %v\n", stream.Active)
    }
    ```
  </Tab>
  <Tab title="curl">

    ```bash
      -H "Authorization: APIKey $GCORE_API_KEY" \
      -H "Content-Type: application/json" \
      -d '{"active": false}'
    ```

    <p>The API returns the updated stream object with `"active": false`.</p>
