## Main principles

<p>Streaming videos using HLS and MPEG-DASH protocols is a simple and cost-effective way to show your video to large audiences. However, this requires the original streams to be in a certain format that browsers do not support natively.</p>

<p>At the same time, WebRTC protocol works in any browser, but it's not as flexible when streaming to large audiences.</p>

<p>Gcore [Video Streaming](https://gcore.com/streaming-platform) supports both WebRTC HTTP Ingest Protocol (WHIP) and WebRTC to HLS/DASH converter, giving you the advantages of these protocols.</p>

<Frame>![A diagram depicting WebRTC converting to LL-HLS/DASH](/images/docs/streaming-platform/live-streaming/protocols/webrtc/diagram-whip-hls-protocols-supported.png)</Frame>

## Advantages of WebRTC and conversion to HLS/DASH

<p>WebRTC ingest for streaming offers two key advantages over traditional RTMP and SRT protocols:</p>

1. It runs directly in the presenter's browser, so no additional software is needed.

2. WebRTC can reduce stream latency.

<p>By using WebRTC WHIP for ingest, you can convert WebRTC to HLS/DASH playback, which provides these benefits:</p>

  * Fast ingest via WebRTC from a browser.
  * Optimal stream distribution using HLS/DASH with [adaptive bitrate streaming](/streaming/live-streams-and-videos-protocols-and-codecs/output-parameters-and-codecs) (ABR) through the CDN.

<Frame>![A diagram depicting WebRTC transcoding and distribution via HLS/DASH](/images/docs/streaming-platform/live-streaming/protocols/webrtc/diagram-how-transcoding-is-configured.png)</Frame>

## How it works

<p>We use a dedicated WebRTC WHIP server to manage WebRTC ingest. This server handles both signaling and video data reception. Such a setup allows you to configure WebRTC on demand and continue to use all system capabilities to set up transcoding and delivery via CDN.</p>

<p>The RTC WHIP server organizes signaling and receives video data. Signaling refers to the communication between WebRTC endpoints that are necessary to initiate and maintain a session. WHIP is an open specification for a simple signaling protocol that starts WebRTC sessions in an outgoing direction, such as streaming from your device.</p>

<p>We use local servers in each region to ensure a minimal route from a user-presenter to the server.</p>

### WebRTC stream encoding parameters

<p>The stream must include at least one video track and one audio track:</p>

  * Video must be encoded using H.264.
  * Audio must use OPUS codec.

<p>If you use [OBS](https://obsproject.com/) or your own WHIP library, use these video encoding parameters:</p>

  * Codec H.264 with no B-frames and fast encoding:

    * **Encoder**: x264, or any of H.264
    * **CPU usage**: very fast
    * **Keyframe interval**: 1 sec
    * **Profile**: baseline
    * **Tune**: zero latency
    * **x264 options**: bframes=0 scenecut=0
  * Bitrate:

    * The lower the bitrate, the faster the data will be transmitted to the server. Choose the optimal value for your video. A typical value is 1-2 Mbps for online training or presenter broadcasts.

<p>You might have these settings in OBS:</p>

<Frame>![Example of listed OBS settings](/images/docs/streaming-platform/live-streaming/protocols/webrtc/example-obs-settings.png)</Frame>

### LL-HLS and LL-DASH outputs

<p>Streams sent via WebRTC are transcoded in the same way as other streams received via RTMP and SRT.</p>

<p>At the output, you can view the streams using any available protocols:</p>

  * **MPEG-DASH**: Â±2-4 seconds latency to a viewer with ABR.
  * **LL-HLS**: Â±3-4 seconds latency to a viewer with ABR.
  * **HLS MPEG-TS**: legacy with [non-low-latency](/streaming/live-streaming/how-low-latency-streaming-works#switch-to-legacy-hls-modes) (Â±10 seconds latency) with ABR.

<p>For WebRTC mode, we use a method of constant transcoding with an initial given resolution. This means that if WebRTC in a viewer's browser reduces the quality or resolution of the master stream (such as 360p) due to restrictions on the viewer's device (such as network conditions or CPU consumption), the transcoder will continue to transcode the reduced stream to the initial resolution (such as 1080p ABR).</p>

<p>When the restrictions on the viewer's device are removed, quality will improve again.</p>

## Start WebRTC to HLS/DASH in your environment

### Start a stream with the Gcore WebRTC WHIP library

<p>Since WHIP is an open standard, many libraries have been released for it in different languages. Use the Gcore WebRTC WHIP client or any other library specified in the [WHIP clients](#supported-whip-clients) section.</p>

<p>We provide a WebRTC WHIP library for working in browsers. It implements the basic calls and simplifies working with WebRTC:</p>

  * Wrapper for initializing WebRTC stream and connecting to the server.
  * Camera and mic wrapper.
  * Monitoring WebRTC events and calling appropriate handlers in your code.

### Start a stream with your own backend or frontend

<p>Get access and data from the microphone and camera:</p>

```js
import { WebrtcStreaming } from 'https://rtckit.gvideo.io/0.89.14/index.esm.js';
const WHIP_ENDPOINT = '{push_url_whip}';
const webrtc = new WebrtcStreaming(WHIP_ENDPOINT, {...});
```

<p>Send a local stream to the WHIP server:</p>

```js
webrtc.openSourceStream({
 audio: mic,
 video: cam,
 resolution: 1080,
})
```

<p>Note that if a user stops streaming to the ingester, such as by closing the browser tab, the stream settings will be terminated. When the user resumes streaming from any browser, the ingester will pick up the stream. However, there will be a brief delay before the ingested stream becomes playable.</p>

<p>If a user tries to stream to the same endpoint where another user is already streaming, the former will get an error message from the media server. The current stream will remain uninterrupted.</p>

Use the `iframe_url`, `hls_cmaf_url`, `hls_mpegts_url`, and `dash_url` fields from the stream response. ## Troubleshooting

<p>If you experience issues related to our streaming service, check out the sections below. They outline common problems and recommended resolution steps.</p>

### Error handling

<p>**NetworkError**</p>

<p>For details, refer to [NetworkError class](https://github.com/G-Core/gcore-webrtc-sdk-js/blob/main/packages/rtckit/docs/api/rtckit.networkerror.md).</p>

<p>The ingestion service is unavailable or is unreachable from the client's network. The error message includes a description of the error cause.</p>

<p>In such cases, the application should render itself unavailable and report the error to Gcore support. The app should not retry the operation, as the retry logic is already implemented in the SDK.</p>

<p>**ServerRequestError**</p>

<p>For details, check out [ServerRequestError class](https://github.com/G-Core/gcore-webrtc-sdk-js/blob/main/packages/rtckit/docs/api/rtckit.serverrequesterror.md).</p>

<p>The ingestion server returned an error, which can be identified by inspecting the `status` and `detail` fields of the error object. WHIP publish requests can also return a non-200 HTTP response, so inspect the HTTP status code and the `X-Reason-Code` response header before retrying.</p>

<Accordion title="Typical cases for ServerRequestError">
| HTTP status code | X-Reason-Code | Explanation | Action |
|------------------|---------------|-------------|--------|
| 400 | N/A | The client request is incorrect. This can happen when the WHIP client sends invalid request parameters. | Check the WHIP client configuration. If the response has no readable description, contact the Gcore support team. |
| 401 | 2001 | Stream does not exist. | Create a stream or use an existing stream's `push_url_whip`. |
| 403 | 2002 | Stream token is invalid. | Copy the current WHIP URL from the stream settings or reset the push token. |
| 403 | 2003 | Someone else is already streaming. | Stop the active publisher or wait about 30 seconds after an unclean disconnect before retrying. |
| 403 | 2004 | Stream is disabled. | Activate the stream in the API or Customer Portal and confirm that `active` is `true`. |
| 403 | 2005 | Client live streams limit reached. | Deactivate unused streams or ask the support team or account manager to increase the limit. |
| 403 | 2006 | Client status is not active. | Check the account status with the support team or account manager. |
| 500, 502, 503, 504, 5xx (infrequently) | N/A | Gcore infrastructure is experiencing pressure or outage. | Contact the Gcore support team. The app should render itself unavailable and must not retry the request. |

</Accordion>

<p>**TimeoutError**</p>

<p>For details, check out [TimeoutError class](https://github.com/G-Core/gcore-webrtc-sdk-js/blob/main/packages/rtckit/docs/api/rtckit.timeouterror.md).</p>

<p>Some operation has timed out.</p>

<Accordion title="Typical cases for TimeoutError">
| Error message | Explanation |
|---------------|-------------|
| Timeout waiting for ICE candidates | **Cause 1**. Incorrectly configured [ICE servers](https://github.com/G-Core/gcore-webrtc-sdk-js/blob/3e45d6e8beebcc7221625bd9e3b3b1749d9405ae/packages/rtckit/docs/api/rtckit.whipclientoptions.md). The default configuration (when no ICE servers are specified) is to fetch a list of them from the WHIP endpoint.<br/><br/> **Cause 2**. ICE servers fetched from the WHIP endpoint are unreachable from your client's location. This is very unlikely to happen.<br/><br/> In both cases, start by checking the ICE servers your WebRTC uses as described in the [Network troubleshooting section](#network-troubleshooting). If that doesn't work, contact the [Gcore support team](mailto:support@gcore.com).<br/><br/> The client app should render itself unavailable due to network conditions as an explanation. |

</Accordion>

<p>Other types of errors are described in our [SDK docs](https://github.com/G-Core/gcore-webrtc-sdk-js/blob/main/packages/rtckit/docs/api/rtckit.md). End-users should not encounter these errors, and there is no way to handle them in a real application apart from reporting the error occurrence.</p>

<p>Some SDK methods might also throw browser's native exceptions, such as [WebrtcStreaming.openSourceStream](https://github.com/G-Core/gcore-webrtc-sdk-js/blob/main/packages/rtckit/docs/api/rtckit.webrtcstreaming.opensourcestream.md) and the methods of the [MediaDevicesHelper](https://github.com/G-Core/gcore-webrtc-sdk-js/blob/main/packages/rtckit/docs/api/rtckit.mediadeviceshelper.md) throw [getUserMedia-originated exceptions](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia#exceptions). The application should handle them accordingly.</p>

### Sudden disconnection of camera or microphone

<p>Sometimes, users use external or plug-in cameras and microphones, and these devices can be disconnected at any time:</p>

  * A USB camera cable might be unplugged.
  * AirPods may be placed back in their case.

<p>If a camera or microphone is accidentally disconnected, you need to track such cases programmatically. Enable the `mediaDevicesAutoSwitch` option and subscribe to the event:</p>

  * set mediaDevicesAutoSwitch: true
  * catch WebrtcStreamingEvents

<p>The new algorithm ensures uninterrupted broadcasting by prompting the browser to switch to another available camera or microphone if the current device becomes unavailable.</p>

<p>When such a situation occurs, you will know which device was disconnected and which one was connected instead. This will allow you to visualize (if necessary) the new connected device in your interface.</p>

### Network troubleshooting

#### Video stream is poorly transcoded or constantly stops

<p>If a stream in the player constantly stops, is interrupted, or has poor quality, the issue is likely related to slow transmission of the original stream from a presenter via WebRTC.</p>

<p>WebRTC is very demanding of the quality of internet connection from client to server. At the same time, standard implementations take into account many parameters on a local device, which can cause slower transmission of data or even stop it altogether until conditions are improved.</p>

<p>To diagnose such situations:</p>

1. Use the **VideoResolutionChangeDetector** plugin. It allows you to show a message about bad network conditions on a viewer's device.

2. Use Chrome's WebRTC debug tool that's available via this link: chrome:\\webrtc-internals.

<p>Network congestion, occurring when resource demand surpasses capacity, leads to packet loss, increased latency, and jitter, hindering real-time communication, with congestion control algorithms optimizing performance by regulating data packet flow. You can read how WebRTC uses Transport Wide Congestion Control (TWCC) to control it in [the article about TWCC](https://bloggeek.me/webrtcglossary/transport-cc/).</p>

<p>The available bitrate is calculated in the **availableOutgoingBitrate** parameter, which indicates the available outbound capacity of the network connection. The higher the value, the more bandwidth you can assume is available for outgoing data. The value is reported in bits per second and is computed over a 1-second interval.</p>

<p>The most likely scenario for quality degradation occurs here when the channel width becomes insufficient to send good resolution.</p>

<p>However, sometimes the connection is even worse when packets are lost. In this case, the server starts sending NACK (Negative Acknowledgement) packets. You can read more about this issue in the [NACK overview article](https://bloggeek.me/webrtcglossary/nack/).</p>

<p>More and more data start to be resent, which leads to increased latency or gaps in frames. In this case, the transcoder doesn't receive frames on time, causing the video to interrupt or stop altogether. You can monitor and debug this issue in Chrome's webrtc-internals tool:</p>

<Frame>![Example graphs in Chrome WebRTC internals tool](/images/docs/streaming-platform/live-streaming/protocols/webrtc/sample-graphs-network-troubleshooting.png)</Frame>

<p>What to do in such situations:</p>

  * Always show users a message about changed conditions. In 99% of cases, the issue is related to the user's internet conditions.
  * Use TCP as the delivery protocol instead of UDP.
  * Use the TURN server for delivery instead of sending directly to the media server.

#### Issues with ICE servers

<p>If you experience problems with timeout waiting for an ICE candidate, check your ICE server configuration.</p>

<p>ICE servers used by the WHIP client can be configured explicitly using the iceServers [configuration option](https://github.com/G-Core/gcore-webrtc-sdk-js/blob/3e45d6e8beebcc7221625bd9e3b3b1749d9405ae/packages/rtckit/docs/api/rtckit.whipclientoptions.md). Otherwise, they are fetched from Gcore's media server in the response to a session initiation request.</p>

<p>In the latter case, check what the server returns in the `Link` headers:</p>

<Frame>![Example data in Link headers](/images/docs/streaming-platform/live-streaming/protocols/webrtc/link-headers.png)</Frame>

```
Link: ; rel="ice-server"
Link: ; rel="ice-server"; username="1730558739:0nu0id47meqbsyvpz743"; credential="IswwB19KAEWQujy3X/c4D9GjZj8="; credential-type="password"
Link: ...
```

<p>You can also inspect the servers using chrome://webrtc-internals or an alternative tool:</p>

<Frame>![Example of servers check in Chrome WebRTC internals](/images/docs/streaming-platform/live-streaming/protocols/webrtc/check-sever-config.png)</Frame>

<p>After you verify your server configuration, use the [Trickle ICE](https://webrtc.github.io/samples/src/content/peerconnection/trickle-ice/) app to test the servers.</p>

<p>Add a STUN or TURN server and check how it works. If everything functions correctly, the results will show:</p>

  * A srvrflx candidate for STUN server
  * A relay candidate for a TURN server

<p>If you don't see these results, your STUN or TURN server may be misconfigured, or there is an outage.</p>

<p>The [Gcore support team](mailto:support@gcore.com) will help you handle that. In the request, include the results of your ICE connectivity check to help us resolve the issue quickly.</p>

## Deactivate a stream

<p>Set `active` to `false` to stop ingest processing. An inactive stream ignores PUSH attempts and cannot be pulled. To permanently remove the stream, use the delete operation instead.</p>

<Tabs>
  <Tab title="Python SDK">
    ```python
    import os
    from gcore import Gcore

    client = Gcore()
    stream = client.streaming.streams.update(
        int(os.environ["STREAM_ID"]),
        stream={"active": False},
    )
    print(f"Active: {stream.active}")
    ```
  </Tab>
  <Tab title="Go SDK">
    ```go
    package main

    import (
    	"context"
    	"fmt"
    	"os"
    	"strconv"

    	gcore "github.com/G-Core/gcore-go"
    	"github.com/G-Core/gcore-go/streaming"
    )

    func main() {
    	client := gcore.NewClient()
    	ctx := context.Background()

    	streamID, _ := strconv.ParseInt(os.Getenv("STREAM_ID"), 10, 64)
    	stream, err := client.Streaming.Streams.Update(ctx, streamID, streaming.StreamUpdateParams{
    		Stream: streaming.StreamUpdateParamsStream{
    			Name:   os.Getenv("STREAM_NAME"),
    			Active: gcore.Bool(false),
    		},
    	})
    	if err != nil {
    		panic(err)
    	}
    	fmt.Printf("Active: %v\n", stream.Active)
    }
    ```
  </Tab>
  <Tab title="curl">
    ```bash
    curl -X PATCH "https://api.gcore.com/streaming/streams/$STREAM_ID" \
      -H "Authorization: APIKey $GCORE_API_KEY" \
      -H "Content-Type: application/json" \
      -d '{"active": false}'
    ```

    <p>The API returns the updated stream object with `"active": false`.</p>
  </Tab>
</Tabs>

## Delete a stream

<p>Permanently remove a stream and all its associated resources.</p>

<Tabs>
  <Tab title="Python SDK">
    ```python
    import os
    from gcore import Gcore

    client = Gcore()
    client.streaming.streams.delete(int(os.environ["STREAM_ID"]))
    print("Stream deleted")
    ```
  </Tab>
  <Tab title="Go SDK">
    ```go
    package main

    import (
    	"context"
    	"fmt"
    	"os"
    	"strconv"

    	if err != nil {
    		panic(err)
    	}
    	fmt.Println("Stream deleted")
    }
    ```
