## About restreams

<p>A restream is a configuration that forwards an active [live&nbsp;stream](/streaming/live-streaming/create-a-live-stream) or playlist from Gcore Streaming to an external service — YouTube, Facebook, Twitch, or any other RTMP, RTMPS, or SRT endpoint — while the Gcore player continues to serve the same stream in parallel.</p>

<Frame>![Restreams to YouTube](/images/docs/streaming/live-streaming/create-and-configure-a-restream-to-social-media/restreaming-youtube.png)</Frame>

<p>Restreaming is useful when the same live event must appear in multiple places at once — a website player, YouTube, and Facebook simultaneously. Instead of managing a separate encoder connection to each destination, one live stream is sent to Gcore Streaming and distributed to all selected targets. This reduces configuration complexity and the risk of mid-broadcast errors.</p>

## Restream workflow

<p>Get the stream URL and stream key from the target service or target media server — or an SRT target URL. Then create a restream in the [Gcore Customer Portal](https://portal.gcore.com), add the target URL, and select the live stream to broadcast. Once saved and the live stream is active, the broadcast appears on the Gcore player and on the target service simultaneously.</p>

<p>Here's how retransmission looks schematically: one stream at the input, many restreams at the output:</p>

```text
                 +-----------------------+
 RTMP/RTMPS      |                       | -------->  Facebook (RTMP)
     or  ------> |    Gcore Streaming    | -------->  YouTube (RTMPS)
 SRT             |                       | -------->  Media server (SRT)
                 +-----------------------+ -------->  Other RTMP/SRT targets
```

<p>**Pricing.** Pricing depends on the number of target destinations — the fewer destinations, the lower the cost. Account limits are described in the [Multiple&nbsp;restreaming](#multiple-restreaming) section below.</p>

<Info>
Supported restreaming combinations:

 - RTMP → RTMP
 - RTMPS → RTMPS
 - RTMP → SRT
 - SRT → SRT
 - SRT → RTMP

For SRT target URLs, only `mode=caller` is supported. Gcore initiates the outbound connection to the external SRT or RTMP target point, so restreaming works as a PUSH from Gcore to the destination.
</Info>

<p>Before configuring a restream, verify that the source stream meets the destination's encoding requirements. A mismatch in bitrate, codec, or keyframe interval causes the destination to reject or drop the incoming feed.</p>

<Warning>
By default, restreaming forwards the source stream to the destination as is. Verify that the source bitrate, codecs, resolution, keyframe interval, and audio format match the destination requirements. To control transcoded output or audio behavior — suppressing audio to avoid copyright claims, for instance — use the REST API.
</Warning>

## Configure a restream

<p>1. Get the stream URL and stream key from the target service. For YouTube, open <a href="https://studio.youtube.com">YouTube Studio</a> → <strong>Go live</strong>, select a streaming software solution, and copy the stream URL and stream key from the upper-right corner. For other services: <a href="https://en-gb.facebook.com/help/587160588142067?helpref=faq_content">Facebook</a>, <a href="https://help.twitch.tv/s/article/twitch-stream-key-faq">Twitch</a>. For SRT targets, get the SRT host, port, and any required query parameters from the target media server administrator.</p>

<Frame>![YouTube Studio stream key shown in the upper-right corner with a Copy button](/images/docs/streaming/live-streaming/create-and-configure-a-restream-to-social-media/Stream_key.png)</Frame>

<p>2. Navigate to the [Restreams](https://portal.gcore.com/streaming/restreams/list) section and click **Create a restream**.</p>

<Frame>![Restreams list page with Create a restream button in the top-right corner](/images/docs/streaming/live-streaming/create-and-configure-a-restream-to-social-media/Create_a_restream.png)</Frame>

<p>The configuration page opens. Complete the remaining steps in it.</p>

<Frame>![Create a restream form with Active toggle, Name, URL, Source, and Select stream fields](/images/docs/streaming/live-streaming/create-and-configure-a-restream-to-social-media/create-restream-form.png)</Frame>

<p>3. The **Active** toggle is enabled by default. Turn it off to save the restream without activating it immediately.</p>

<p>4. Enter a name for the restream.</p>

<p>5. Enter the credentials from step 1. For RTMP/RTMPS, the **URL** field expects the stream URL and stream key concatenated — the [URL&nbsp;format](#rtmp-target-url-format) section below explains the pattern. For SRT, the format is covered in [SRT&nbsp;parameters](#srt-target-url-parameters).</p>

<p>6. Select the content type to restream: live streams or playlists.</p>

<Note>
Playlists must be looped to be available for restreaming.
</Note>

<p>7. Select a stream or playlist from the drop-down list.</p>

<p>8. Click **Create**.</p>

<p>Enable the live stream or playlist, wait a few minutes for the settings to apply, then reload the <a href="https://portal.gcore.com/streaming/restreams/list">Restreams</a> page. When set up correctly, the <strong>Live</strong> label appears.</p>

<Frame>![Restreams list showing a restream with Live status indicator](/images/docs/streaming/live-streaming/create-and-configure-a-restream-to-social-media/Live.png)</Frame>

<p>To restream again after the broadcast ends, no reconfiguration is needed if the stream key and URL have not changed. If the key or URL has changed, open the restream settings to update the credentials: click **⋯** next to the restream and select **Settings**.</p>

<Frame>![Restream settings modal showing Active toggle, Name, URL, Source, and Save button](/images/docs/streaming/live-streaming/create-and-configure-a-restream-to-social-media/restream-settings.png)</Frame>

## RTMP and SRT restream targets

<p>Use RTMP or RTMPS for social media destinations and short, stable network paths. Most major platforms accept RTMP ingest and it works well for moderate bitrates and local routes.</p>

<p>For cross-country or cross-continental delivery where RTMP can become unstable, SRT provides reliable retransmission and allows explicit tuning of the recovery window via `latency`. The trade-offs are described in [RTMP&nbsp;vs&nbsp;SRT](/streaming/live-streaming/protocols/rtmp-srt).</p>

### RTMP and RTMPS target URL format

<p>For RTMP and RTMPS targets, enter the URL and stream key as follows:</p>

```text
rtmp://<hostname_or_IP>[:<port>]/<application_name>/<stream_key_or_stream_name>
rtmps://<hostname_or_IP>[:<port>]/<application_name>/<stream_key_or_stream_name>
```

<p>If the stream URL is `rtmp://a.rtmp.youtube.com/live2` and the stream key is `ab123-cde4-f56g-hi78-90j`, the URL field contains:</p>

<Frame>![RTMP URL field with stream URL and stream key concatenated](/images/docs/streaming/live-streaming/create-and-configure-a-restream-to-social-media/rtmp.png)</Frame>

<p>where:</p>

  * `rtmp://a.rtmp.youtube.com/live2` is the URL
  * `/` is the separator
  * `ab123-cde4-f56g-hi78-90j` is the stream key

### SRT target URL parameters

<p>For SRT restreams, add the parameters required by the target endpoint directly to the SRT URL query string. Common parameters include:</p>

- `mode=caller`
- `latency`
- `send_buffer_size`
- `pkt_size`
- `passphrase`
- `streamid`

<p>Example:</p>

```text
srt://target.example.com:5001?streamid=1&mode=caller&latency=2500000&passphrase=secret
```

<p>The target media server defines which parameters are required.</p>

### SRT latency

<p>For SRT restreams, specify `&latency=N` explicitly in the SRT target URL instead of relying on a default value. It sizes the recovery buffer for round-trip time, jitter, and packet loss on the route to the target site.</p>

<p>The right latency value depends on the geographic distance and network conditions between Gcore and the target destination, especially for cross-continental routes. The target service may have specific latency recommendations — follow those when available.</p>

| Network conditions  | Recommended latency |
|---------------------|---------------------|
| Cross-region        | 1–2 seconds         |
| Public internet     | 2–5 seconds         |

<p>SRT latency selection is covered in the [SRT&nbsp;latency&nbsp;guide](/streaming/live-streaming/protocols/srt#best-practices-for-configuring-srt-latency).</p>

<Info>
The target SRT server can accept the latency value in seconds, milliseconds, or microseconds — check the target server's documentation for the accepted format:

- Seconds: `2.5`
- Milliseconds: `2500`
- Microseconds: `2500000`
</Info>

## Target URI format

<p>The `uri` field determines the destination protocol and address.</p>

<p>**RTMP/RTMPS** — use for YouTube, Facebook, Twitch, and most social platforms:</p>

```text
rtmp://<hostname>[:<port>]/<app>/<stream_key>
rtmps://<hostname>[:<port>]/<app>/<stream_key>
```

<p>Example for YouTube: `rtmp://a.rtmp.youtube.com/live2/{YOUR_STREAM_KEY}`</p>

<p>**SRT** — use for cross-continental delivery or when RTMP becomes unstable:</p>

```text
srt://<hostname>:<port>?mode=caller&latency=<microseconds>&streamid=<ID>
```

<p>Common SRT parameters: `mode=caller` (required), `latency` (2 500 000 = 2.5 s recommended for public internet), `passphrase`, `streamid`, `pkt_size`. Match these to what the target media server requires.</p>

<p>Pass the assembled URI in the `uri` field when creating a restream.</p>

## Create a restream

<p>Send `POST /streaming/restreams` with the target URI, source stream ID, a name, and `active: true` to start restreaming immediately. Set `active: false` to configure without activating yet. Set `source` to `"transcoded"` to restream the processed version of the stream (with overlays applied, using the highest ladder resolution); the default is `"original"`.</p>

<p>To control the audio track (to prevent copyright claims on destinations like YouTube), configure `no_audio` and `no_audio_mode`:</p>

- **no_audio** (boolean): Set to `true` to remove or replace the source audio track. Default is `false`. Accepts strict boolean values only; other values return HTTP 422.
- **no_audio_mode** (string): Determines handling when `no_audio: true`. Options are `"drop"` (default; strips the audio track completely) or `"silence"` (replaces audio with silence).

<Tip>
YouTube rejects incoming streams with no audio track. When restreaming to YouTube with audio removed, set `no_audio_mode: "silence"`.
</Tip>

  <Tab title="Python SDK">
```python
import os
from gcore import Gcore

client = Gcore()
stream_id = int(os.environ["STREAM_ID"])

resp = client.streaming.restreams.with_raw_response.create(
    restream={
        "name": "YouTube restream",
        "uri": "rtmp://a.rtmp.youtube.com/live2/{YOUR_STREAM_KEY}",
        "stream_id": stream_id,
        "active": False,
        "source": "original",
    }
)
data = resp.http_response.json()
restream_id = data["id"]
print(f"Restream ID:   {restream_id}")
print(f"Target URI:    {data['uri']}")
print(f"Active:        {data['active']}")
```

## Multiple restreaming

Technically, the number of restreams is not limited. The default account limit is three restreams. To increase this limit, contact [technical&nbsp;support](mailto:support@gcore.com) and specify the number of restreams needed. Gcore support will update the limit and notify when the change is active.

## Source stream recovery

If the source stream becomes unavailable, Gcore retries the source before stopping the restream.

**Recovery behavior:**

- Original stream is active.
- If the original stream is unavailable and is down for more than ±3 seconds, the retry mechanism activates.
- The system retries the source stream for approximately 60 minutes:
  - If the original stream recovers, the timer resets and restreaming resumes automatically.
  - Otherwise the restream stops permanently. To resume it, activate it manually or via API.

## Restream troubleshooting

### RTMP targets

**Common issues:**

- **Destination drops the stream**: RTMP destinations terminate the stream when delivery is too slow or unstable. For public internet routes, bitrates above 5 Mbps frequently cause interruptions; a practical limit for stable delivery is 1–3 Mbps.
- **Long-distance instability**: High latency, jitter, or packet loss on cross-continental paths causes buffering and disconnects. For these routes, SRT is more reliable — the [protocol&nbsp;guide](#rtmp-and-srt-restream-targets) covers the trade-offs.

**Solutions:**

- Keep the source bitrate within the range the destination and network route can sustain.
- For long-distance or unstable routes, switch the restream URI to an SRT endpoint.

Typical packet-loss pattern for RTMP over a long-distance connection:

<Frame>
![RTMP falls](/images/docs/streaming/live-streaming/create-and-configure-a-restream-to-social-media/restreaming-abroad.jpeg)
</Frame>

### SRT targets

**Common issues:**

- **Wrong SRT mode**: Gcore supports only `mode=caller` for SRT restream targets. The destination must listen for the incoming SRT connection.
- **Latency too low**: Long-distance paths have high RTT, jitter, or packet loss. If `latency` is too low, retransmitted packets arrive late and the target may report TS loss or dejitter buffer resets.
- **Target bandwidth lower than source bitrate**: Restreaming sends the source stream as-is. Use a lower-bitrate source or a transcoded stream if the target cannot sustain the full bitrate.
- **Firewall or UDP filtering**: SRT uses UDP; the target host and network must allow inbound UDP on the configured port.
- **Encryption mismatch**: If the target requires encryption, `passphrase` and `pbkeylen` must match the target configuration.

**Solutions:**

- Use `mode=caller` in the SRT target URI.
- Increase `latency` to a value appropriate for the route — the [SRT&nbsp;latency](#srt-latency) section lists recommended ranges.
- Verify UDP reachability to the target SRT port.
- Match all required target parameters: `streamid`, `passphrase`, `pbkeylen`, `pkt_size`, buffer settings.

### Facebook

**Common issues:**

- **Expired or invalid stream key**: The connection is rejected if the event is marked finished in Facebook UI or the stream key was regenerated.
- **Keyframe interval exceeds 4 seconds**: Facebook enforces a maximum GOP size of 4 seconds.
- **Unstable or insufficient bitrate**: Significant drops may cause Facebook to terminate the stream.
- **Incorrect event configuration**: Using an outdated or incorrect stream key leads to immediate connection failure.

**Solutions:**

- Confirm the stream key is active and the event is in *Live* or *Preview* state.
- Set keyframe interval to **2 seconds** (recommended) or 4 seconds (maximum).
- Maintain a stable, constant bitrate.
- Update stream keys after Facebook regenerates them.

[Facebook&nbsp;live&nbsp;docs](https://www.facebook.com/business/help/162540111070395?id=1123223941353904) cover additional requirements and limits.

### YouTube

**Common issues:**

- **Invalid stream key or inactive event**: YouTube rejects connections when the key is incorrect or the event is not yet open.
- **Missing audio track**: YouTube rejects incoming streams that lack an audio track. When disabling restream audio via API, `no_audio_mode` must be set to `"silence"`.
- **Unsupported codec or profile**: YouTube requires H.264 (Baseline/Main/High) and AAC audio.
- **Unstable input bitrate**: Bitrate drops cause buffering and disconnects.
- **High keyframe interval**: YouTube recommends a GOP of **2 seconds**.

**Solutions:**

- Verify the stream key and event status before connecting.
- When disabling audio on a restream to YouTube, set `no_audio_mode: "silence"` instead of dropping the audio track.
- Use H.264 + AAC encoding.
- Set keyframe interval to **2 seconds**.
- Verify encoder output is stable and avoids bitrate spikes.

[YouTube&nbsp;encoder&nbsp;settings](https://support.google.com/youtube/answer/2853702) list the full codec and bitrate requirements.

### Twitch

**Common issues:**

- **Rate limiting**: Frequent connection attempts may trigger temporary limits.
- **Excessive bitrate**: Twitch recommends a maximum of **6000 Kbps** for non-partners.
- **Unsupported codec settings**: Twitch requires H.264 + AAC.
- **Disconnects due to unstable upstream**: Twitch is sensitive to jitter and packet loss.

**Solutions:**

- Keep bitrate at or below 6000 Kbps.
- Use a two-second keyframe interval and H.264 + AAC.
- If Twitch disconnects due to upstream instability, consider switching to a closer Twitch ingest server.

[Twitch&nbsp;broadcasting&nbsp;guidelines](https://help.twitch.tv/s/article/broadcasting-guidelines) list ingest server addresses and bitrate requirements.

### Other platforms

**Common issues:**

- Stream key expired or rotated — the destination rejects the connection immediately.
- GOP size exceeds the destination's limit — most platforms require a keyframe interval of **2 seconds**.
- Destination accepts only a specific RTMP variant (RTMP vs RTMPS) or requires a non-standard port.

**Solutions:**

- Verify the stream key is current before starting the restream.
- Use a two-second keyframe interval unless the destination specifies otherwise.
- Check the destination's RTMP ingest documentation for the required URL scheme and port.
