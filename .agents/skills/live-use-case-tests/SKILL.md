  how-to tabs. Use when adding or changing an API or Terraform MethodSection,
  when a live test fails, when onboarding a new how-to, or when the user asks

Write live tests that execute the **same code the article shows customers**.
If that code does not run against the live API, SDK, or Terraform provider,
the article is wrong. Fix the article. Do not weaken, skip, or rewrite the
test to match a broken sample.

## Hard rule (do not paraphrase)

тесты не должны подгоняться под кривой код в статье, а наоборот это сигнал, чтобы статью исправить правильно. потому что мы даем код клиентам.

The how-to is customer-facing. A failing live call is a documentation bug
until proven otherwise (quota, outage, leftover resource). Proven otherwise
is rare. Default action: correct the MDX sample, then write the test to that
corrected sample.

Forbidden:

- `skip:` because the sample does not compile or apply
- `extra_body` / `WithJSONSet` / a different resource name in the test while
  the article still shows the typed kwargs, the invented field, or the
  read-only attribute
- Pinning a heading and never applying that HCL / never calling that SDK
  method
- Refreshing sample snapshots so a green run hides a sample that was never
  executed

Allowed after the article is fixed: documenting the **real** SDK/provider
surface in the MDX (for example `extra_body` when typed params omit a field
the REST body accepts, or `sftp_password` when `password` is read-only).
The test then runs that same code.

The live orchestrator in the tests repo must not auto-edit MDX. This skill
**does** edit MDX when the sample is the bug.

1. This SKILL.md

3. The article `.mdx` under test

## Two working modes

### A — This docs repo only (typical contributor)

There is no access to `docs-live-use-cases`. Produce a **pickup pack** the
owner can copy:

```
_planning/live-use-cases/{product}/{section}/{slug}/
  NOTES.md
  scenario.yaml
  python/cases.py
  curl/cases.py
  go/happy_test.go
  terraform/cases.py     # omit if the article has no Terraform tab
```

Same layout as the tests repo (`use_cases/...`), minus `catalog.yaml` (the
owner adds the row) and minus `samples/` (generated by `--refresh-samples`).

`NOTES.md` lists: article path, what was live-verified, leftovers deleted,
and any article fix you already applied.

Do not put credentials, `.env`, or real API keys in this pack.

### B — Tests repo is available

Implement under `C:\Projects\docs-live-use-cases` (or `DOCS_LIVE_DOCS_ROOT`
sibling). Add the `catalog.yaml` row, run live, pin samples. Still fix MDX
in **this** repo when a sample is wrong. Two repos, one article.

## When to load this skill

- After `.agents/skills/api-use-case/SKILL.md` or
  `.agents/skills/terraform-use-case/SKILL.md` finishes a tab
- User asks to add, update, or fix live tests for a how-to
- Live run is `failed` or `drift`
- New API or Terraform headings appeared in an already catalogued article

Do not write tests for Portal-only articles. Do not catalog an article that
has no `<MethodSection id="api">`. Terraform-only extra headings still need
a Terraform scenario once the API tab exists.

GPU / Bare Metal GPU how-tos: `pool: gpu`. Do not run them unless the user
explicitly asks. Do not discuss GPU Cloud beyond that pool flag.

## Phase 1 — Read the article as a customer

Read the full MDX. For each heading in `<MethodSection id="api">` and
`<MethodSection id="terraform">` that contains an executable fence
(`python`, `go`, `bash`, `hcl`):

- Record the heading text (anchors are heading strings, not line numbers)
- Record the tab title (`Python SDK`, `Go SDK`, `curl`, `Terraform`)
- Copy the fence. That is the contract.

Quickstart and Step-by-step that create the same resource = **one** e2e
scenario (`covers:` the other heading). Independent operations = separate
scenarios.

---

## Phase 2 — Prove the sample before you encode it

Run the article code against live, or the closest equivalent:

| Tab | Prove with |
|-----|------------|
| Python SDK | `venv`, `Gcore()`, the methods in the fence |
| Go SDK | `gcore.NewClient()`, the methods in the fence |
| curl | real `curl` to `https://api.gcore.com` |
| Terraform | provider **v2 only**, `terraform apply` then destroy |

SDK field names must exist in the installed SDK. Terraform attributes must
exist as **writable** in provider v2 (read-only computed fields are not
inputs).

If the fence fails:

1. Stop writing the test.
2. Fix the MDX so a customer can paste it.
3. Re-run the fixed sample.
4. Only then write the test.

Delete throwaway resources in `finally` / `defer` / empty `main.tf` apply.
Leftovers are a test bug.

---

## Phase 3 — Encode scenarios

Write `scenario.yaml` from headings. Do not invent tabs.

- `tier: smoke` — list/get, empty list is valid
- `tier: e2e` — create, assert required fields, mutate if the article does,
  delete
- Missing tab = `skip:` with a factual reason (`No Terraform tab.`,
  `Terraform tab does not list locations.`). Not `skip:` because you have
  not implemented it yet unless the owner asked to defer **after** python
  and curl are green
- `sample_headings:` for every fence the e2e actually executes
- Unique names. Product-specific limits (SFTP `{client_id}-{name}` length,
  globally unique bucket names) belong in a helper, not ad-hoc strings

Entry names: Python/curl `snake_case` functions; Go `TestPascalCase`.

Details: [reference.md](reference.md).

---

## Phase 4 — Update existing tests

When the article changed:

1. Diff the pinned fence against current MDX (`drift` means the pin is stale
   or the heading was renamed).
2. Change `cases.py` / Go tests / Terraform HCL **to the new article**.
3. If the new article sample does not run — go back to Phase 2 (fix MDX).
4. `--refresh-samples --article {slug}` only after test code follows the
   new sample.
5. Live-run that article. `--scan-coverage` so new headings are a scenario,
   a `covers:` entry, or an explicit skip.

Do not refresh first and hope.

---

## Phase 5 — Done

Mode A: pickup pack under `_planning/live-use-cases/...` plus any MDX fixes.

Mode B: catalog row, live green for the clients you enabled, samples pinned,
no leftover resources.

Report:

```
Article: [path]
Scenarios: [ids]
Clients: python / go / curl / terraform (skips + reasons)
Article fixes: [none | list]
Pickup pack: [path or n/a — implemented in tests repo]
Leftovers: none
```
