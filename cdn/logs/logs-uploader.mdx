<p>Logs Uploader exports CDN request and cache logs to a storage destination as they arrive. When [Origin&nbsp;Shielding](/cdn/cdn-resource-options/general/enable-and-configure-origin-shielding) is enabled and the policy includes those logs, the export also contains requests processed by mid-tier cache servers.</p>

<p>To export logs, create a policy that defines what to export, connect a target that receives the logs, then create a configuration that links them to CDN resources.</p>

<p>Accounts that already use the hourly [Raw Logs](/cdn/logs/raw-logs-export-cdn-resource-logs-to-your-storage) export to Amazon Simple Storage Service (S3), File Transfer Protocol (FTP), or SSH File Transfer Protocol (SFTP) can keep that configuration. Use Logs Uploader for new setups. To migrate an existing Raw Logs export, contact [Gcore&nbsp;Support](mailto:support@gcore.com).</p>

<Note>
Logs Uploader must be enabled for the account before the configuration UI is available. Contact [Gcore&nbsp;Support](mailto:support@gcore.com) or use **Contact support** on the Logs Uploader page in the [Gcore Customer Portal](https://portal.gcore.com).
</Note>

## Create a policy

<p>A policy selects the log fields, the file name format, and how often files rotate. The **Time interval** is 5–60 minutes and defaults to 5. If no requests arrive during an interval and **Include empty logs** is selected, Logs Uploader sends an empty file of about 20 bytes.</p>

<p>In the [Customer&nbsp;Portal](https://portal.gcore.com), open **CDN** → **Logs** → **Logs Uploader**, then **Policies**, and click **Add policy**.</p>

1. Enter a name.
2. Leave **Include empty logs** cleared to skip empty intervals, or select it to confirm delivery when there is no traffic.
3. Select **Include logs from origin shielding** when Origin Shielding is [enabled](/cdn/cdn-resource-options/general/enable-and-configure-origin-shielding) and those mid-tier requests should appear in the export.
4. Choose the log fields. The [field table](#log-schema-and-field-definitions) lists each field and its meaning.
5. Set delimiter, separator, file name format, time interval, and file size limit. The size limit applies before compression — the delivered file can be up to 99% smaller.
6. Click **Add policy**.

<p>To change an existing policy, open it by name. The same settings apply; click **Save changes** when done.</p>

## Create a target

<p>A target is the destination. `Authentication complete` means Logs Uploader can reach and authenticate to that destination — it does not mean a log file has arrived.</p>

<p>On the **Targets** tab, click **Add target**, enter a name, and configure one destination:</p>

<Tabs>
  <Tab title="S3 Gcore">
    [Gcore&nbsp;Object&nbsp;Storage](https://gcore.com/storage)

    1. Select **HTTP** or **HTTPS** and specify the **Endpoint**.
    2. Enter the **Access key ID** and **Secret Access Key**.
    3. Enter the storage **region** and an existing **bucket**.
    4. Optionally, specify an existing **folder** inside the bucket.

    <Info>
      Connection details appear when the storage is [created](/storage/create-an-s3-or-sftp-storage#object-storage). Endpoint, region, and new keys are available from **⋯** on the Object Storages table.
    </Info>
  </Tab>
  <Tab title="S3 OSS">
    [Alibaba&nbsp;Cloud&nbsp;OSS](https://www.alibabacloud.com/en/product/object-storage-service?_p_lc=1)

    1. Enter the **Access Key ID** and **Secret Access Key**.
    2. Enter the **cloud region** and an existing **bucket**.
    3. Optionally, specify an existing folder inside the bucket.

    <Info>
      Alibaba documents [OSS&nbsp;AccessKey](https://www.alibabacloud.com/help/en/sls/developer-reference/access-key) pair creation.
    </Info>
  </Tab>
  <Tab title="SLS">
    [Alibaba&nbsp;Cloud&nbsp;SLS](https://www.alibabacloud.com/en/product/log-service)

    1. Enter the **Region** (such as `cn-hangzhou`).
    2. Enter the **Project** name (3–63 characters; lowercase letters, digits, and hyphens).
    3. Enter the **Logstore** name (3–36 characters; lowercase letters, digits, hyphens, and underscores).
    4. Enter the **Access Key ID** and **Secret Access Key**.
    5. Optionally, enter the **Endpoint** to override `region.log.aliyuncs.com`, and a **Topic** (up to 128 characters).

    <Info>
      Alibaba documents [SLS&nbsp;AccessKey](https://www.alibabacloud.com/help/en/sls/developer-reference/access-key) pair creation and project setup in the [SLS&nbsp;quick&nbsp;start](https://www.alibabacloud.com/help/en/sls/getting-started/getting-started-with-simple-log-service).
    </Info>
  </Tab>
  <Tab title="S3 Other">
    Generic S3-compatible object storage

    1. Select **HTTP** or **HTTPS** and specify the **Endpoint**.
    2. Enter the **Access Key ID** and **Secret Access Key**.
    3. Enter the storage **region** and an existing **bucket**.
    4. Optionally, specify an existing folder inside the bucket.
  </Tab>
  <Tab title="FTP">
    <Warning>
      FTP transmits credentials and log data without transport encryption. Use SFTP or HTTPS when logs contain IP addresses, cookies, or request URLs.
    </Warning>

    1. Enter the **Hostname**, **Login**, and **Password**.
    2. Optionally, specify an existing destination directory.
  </Tab>
  <Tab title="SFTP">
    1. Enter the **Hostname** and **Login**.
    2. Authenticate with a **Password**, or with a **Private Key** and **Passphrase**.
    3. Optionally, specify an existing destination folder.
  </Tab>
  <Tab title="HTTP(S)">
    <Warning>
      Plain HTTP transmits log data without transport encryption. Use HTTPS when logs contain IP addresses, cookies, or request URLs.
    </Warning>

    1. Select **POST** or **PUT**, then **HTTP** or **HTTPS**, and specify the **Endpoint**.
    2. Add custom headers if the receiver requires them.
    3. Turn on **Authentication** for token-based header auth, and **Use compression** to gzip the JSON body (up to 99% smaller).
  </Tab>

<p>Click **Add target**. A green `Authentication complete` status confirms the destination is reachable. Click the refresh icon next to the status to run the check again.</p>

<p>To change an existing target, open it by name. The same connection settings apply.</p>

## Create a configuration

<p>A configuration links one policy and one target to CDN resources and starts delivery.</p>

<p>On the **Configurations** tab, click **Add configuration**.</p>

1. Enter a name.
2. Cover **All Resources** (including resources created later) or select **Specific Resource(s)** from the list.
3. Select the policy and the target.
4. Leave **Enable configuration** on to start delivery, or turn it off to save the setup inactive.
5. Click **Add configuration**.

<p>The **Status** column repeats the linked target's authentication state. To change an existing configuration, open it by name — the same resource, policy, and target settings apply.</p>

## Verify delivery

<p>Generate traffic to a CDN resource covered by the configuration. After one full time interval, check the destination for a new file or HTTP POST and confirm the expected fields. `Authentication complete` is not proof that a file arrived — see [Troubleshooting](#troubleshooting) if the destination stays empty.</p>

## Disable or delete a setup

<p>Use **⋯** on a configuration to **Disable** delivery without deleting the setup, or **Enable** it again. The same switch is in the configuration form.</p>

<p>Delete the configuration first. A policy or target that is still linked to a configuration cannot be deleted. Then delete the unused target or policy from **⋯** on its row.</p>

## Log schema and field definitions

<p>The exported log schema includes standard CDN request fields, internal status codes, and format examples.</p>

<AccordionGroup>
  <Accordion title="Log format example">
    The format below is a non-exhaustive example. It does not include every available field — for instance, `$timestamp_request_start`, `$masked_remote_addr`, `$query_string`, and `$quic` are in the field table but not shown here. The actual log output depends on which fields are selected, their order, and the delimiter and separator configured in the policy. New fields may appear at the end of the line; when fields are added to logs, an email notification is sent about the update.

    ```text
    "$remote_addr" "-" "$remote_user" "[$time_local]" "$request" "$status"  
    "$body_bytes_sent" "$http_referer" "$http_user_agent" "$bytes_sent"  
    "$edgename" "$scheme" "$host" "$request_time"  
    "$upstream_response_time" "$request_length" "$http_range" "[$responding_node]"  
    "$upstream_cache_status" "$upstream_response_length" "$upstream_addr"  
    "$gcdn_api_client_id" "$gcdn_api_resource_id" "$uid_got" "$uid_set"  
    "$geoip_country_code" "$geoip_city" "$shield_type" "$server_addr" "$server_port"  
    "$upstream_status" "-" "$upstream_connect_time" "$upstream_header_time"  
    "$shard_addr" "$geoip2_data_asnumber" "$connection" "$connection_requests"  
    "$http_traceparent" "$http_x_forwarded_proto" "$gcdn_internal_status_code" "$ssl_cipher"  
    "$ssl_session_id" "$ssl_session_reused" "$sent_http_content_type" "$tcpinfo_rtt" 
    "$server_country_code" "$gcdn_tcpinfo_snd_cwnd" "$gcdn_tcpinfo_total_retrans" "$gcdn_rule_id"
    "$request_completion" "$gcdn_finalize_reason"
    ```

  <Accordion title="Log schema versioning">
    For HTTP(S) targets, Logs Uploader sends a JSON request payload to the configured endpoint. The `v` field in the payload identifies the schema version — for example, `"v":"10"`. This metadata belongs to the JSON envelope rather than the selectable CDN log fields, so it does not appear in the log format example or field table.

    The version increments when fields are added, renamed, or removed. New fields are added in a backward-compatible way where possible, so most schema changes do not require parser updates. Breaking changes are announced in advance through standard CDN update notifications. Check the `v` value in downstream parsers before processing a batch with an unsupported schema version.

    **HTTP(S) payload structure**

    Each request delivers one batch of log lines. The payload is a JSON object whose `logs` array contains the raw log lines selected and formatted by the policy (the same text that would appear in a file delivered to an S3 or FTP target). The `v` field identifies the schema version of the envelope itself, not the log line format.

    ```json
    {
      "v": "10",
      "logs": [
        "\"203.0.113.45\" \"-\" \"-\" \"[14/Sep/2026:09:47:40 +0000]\" \"GET /image.png HTTP/1.1\" \"200\" \"1514848\"",
        "\"198.51.100.7\" \"-\" \"-\" \"[14/Sep/2026:09:47:42 +0000]\" \"GET /style.css HTTP/1.1\" \"304\" \"0\""
      ]
    }
    ```

    The receiver must return a `2xx` HTTP status code. Any other status code is treated as a delivery failure; Logs Uploader retries the batch and records the error in delivery logs accessible through [Gcore&nbsp;Support](mailto:support@gcore.com).

    <Note>
      If **Use compression** is enabled on the HTTP(S) target, the request body is gzip-compressed and the `Content-Encoding: gzip` header is included. Decompress the body before parsing.
    </Note>
  </Accordion>
</AccordionGroup>

## WAAP log fields

<p>When a CDN resource has [WAAP](/waap) enabled, Logs Uploader appends WAAP security event fields to each request log line. CDN access data and the matching WAAP verdict share one entry — no separate file and no extra Logs Uploader setup.</p>

<p>WAAP fields appear only when **WAAP Status** is Active on **CDN** → **CDN resources**. The toggle is in that resource's **Security** settings. After WAAP is enabled, the next exported batch includes the new fields at the end of the line, so positional parsers keep working. Parsers that reject unknown columns must accept the WAAP fields first. The `v` field in HTTP(S) payloads increments when the schema changes.</p>

<Note>
DDoS protection logs are not exported through Logs Uploader. Only per-request WAAP security events are included. DDoS attack analytics remain available through the WAAP API and dashboard.
</Note>

<AccordionGroup>
  <Accordion title="WAAP fields">
    The following fields are appended to each request log line when WAAP is enabled on the resource.

    | Field                          | Log value example           | Description                                                                                                                                          |
    | :--------------------------------- | :------------------------------ | :------------------------------------------------------------------------------------------------------------------------------------------------------- |
    | `$waap_id`                         | `7f3c1e92-...`                  | Unique WAAP request identifier. Correlate a log line with the [WAAP&nbsp;Request&nbsp;Details](/api-reference/waap/analytics/get-request-details) API |
    | `$waap_decision`                   | `blocked`                       | Final security decision computed by WAAP at the edge. See **Decision and optional action values** below for the full value list and semantics |
    | `$waap_optional_action`            | `captcha`                       | Additional action that was returned to the client alongside the decision (CAPTCHA or non-interactive challenge). See **Decision and optional action values** below |
| `$waap_passed_incident_id`         | `9a8b4f70-...`                  | Identifier of a previous WAAP incident that the request passed — for instance after a successful CAPTCHA solve in an earlier request from the same session. Empty if not applicable |
| `$waap_request_type`               | `regular`                       | WAAP request classification (`regular`, `injected`) |
    | `$waap_country`                    | `DE`                            | ISO 3166-1 alpha-2 country code of the client IP, resolved by WAAP |
    | `$waap_organization`               | `Deutsche Telekom AG`           | Network organization that owns the client IP, resolved by WAAP |
    | `$waap_range`                      | `203.0.113.0/24`                | Network range associated with the client IP |
    | `$waap_session_id`                 | `8c1f0d2a-...`                  | WAAP session identifier. Groups successive requests that WAAP attributes to the same client |
    | `$waap_session_request_number`     | `42`                            | Sequence number of this request within the WAAP session |
    | `$waap_conviction_action`          | `block`                         | Action prescribed by the matched rule. Possible values include `allow`, `block`, `monitor`, `captcha`, `handshake`. Empty if no rule matched |
    | `$waap_conviction_rule_id`         | `100245`                        | ID of the WAAP rule that matched the request |
    | `$waap_conviction_rule_name`       | `SQLi attempt`                  | Human-readable name of the matched WAAP rule |
    | `$waap_conviction_scope`           | `policy`                        | Scope at which the rule was applied (`policy`, `global`, `custom`) |
    | `$waap_conviction_reference_id`    | `signature:sqli-101`            | Reference identifier of the conviction (rule signature, tag, or template reference) |
    | `$waap_conviction_incident_id`     | `4d2e8b1c-...`                  | Identifier of the WAAP incident raised for this request |
    | `$waap_conviction_template`        | `OWASP CRS`                     | Template or ruleset family the matched rule belongs to |

    <Tip>
      All WAAP fields are best-effort: a field is empty (`""`) when WAAP did not compute a value for the request — no rule matched, or the request was served before WAAP analysis completed. Treat empty values as "not applicable", not "zero".
    </Tip>
  </Accordion>
  <Accordion title="Decision and optional action values">
    The `$waap_decision` field gives the final security verdict that WAAP applied at the edge:

    | Value     | Meaning                                                                                                                                                |
    | :------------ | :----------------------------------------------------------------------------------------------------------------------------------------------------------- |
    | `passed`      | Request was allowed because it matched a previously cleared WAAP incident — the client had already solved a CAPTCHA for an earlier request in the same session. The original incident identifier is exported in `$waap_passed_incident_id` |
    | `allowed`     | Request was explicitly allowed by a matched WAAP rule |
    | `monitored`   | Request was logged in monitor mode without applying the rule action. Useful for shadow testing rules before enforcement |
    | `blocked`     | Request was blocked at the edge, or a challenge was issued and is pending client resolution (see the note below) |
    | empty (`""`)  | No WAAP verdict was produced for this request — traffic that did not go through WAAP analysis |

    The `$waap_optional_action` field describes any additional action applied alongside the decision:

    | Value     | Meaning                                                                                                                                                |
    | :------------ | :----------------------------------------------------------------------------------------------------------------------------------------------------------- |
    | `captcha`     | A CAPTCHA challenge was served to the client |
    | `challenge`   | A non-interactive challenge was issued — a JavaScript or cookie handshake |
    | empty (`""`)  | No additional action was applied |

    <Note>
      Challenged requests are recorded as `blocked`. Logs are written at the edge as soon as the response is sent, before WAAP knows whether the client will solve the challenge. When the client passes the challenge, subsequent requests from the same session are exported with `$waap_decision="passed"` and `$waap_passed_incident_id` pointing back to the original incident. Trace the final outcome by joining the two log lines on the session identifier. The full per-incident result is also available through the [WAAP&nbsp;Request&nbsp;Details](/api-reference/waap/analytics/get-request-details) API.
    </Note>
  </Accordion>
</AccordionGroup>

## Troubleshooting

<p>`Authentication complete` confirms that Logs Uploader can reach the destination. It does not mean a log file has arrived.</p>

<p>Files are written at the end of the policy **Time interval** (minimum 5 minutes). Wait at least one full interval after generating CDN traffic.</p>

<p>If the covered resources receive no requests during an interval and **Include empty logs** is off, no file is sent. Turn the option on in the policy to confirm delivery without traffic. An empty file is about 20 bytes.</p>

<p>For S3, FTP, SFTP, and SLS, the bucket, directory, or logstore must already exist — Logs Uploader does not create missing paths. The credentials must allow writes: `s3:PutObject` (and often `s3:GetBucketLocation`) on S3, write access to the FTP/SFTP directory, or `Write` on an SLS logstore.</p>

<p>An HTTP(S) receiver must return `2xx` before the request times out. Any other status is a delivery failure and is retried. If compression is on, the receiver must accept `Content-Encoding: gzip`.</p>

<p>A configuration limited to **Specific Resources** only exports those resources. **All Resources** includes resources created later.</p>

<p>Delivery error details are not shown in the portal. Contact [Gcore&nbsp;Support](mailto:support@gcore.com) for delivery logs for a target or time range.</p>

## Create a Logs Uploader configuration

<p>Create a policy (`rotate_interval_minutes` is 5–60), an HTTP target, and a configuration for one CDN resource. Other `storage_type` values include `s3_gcore`, `s3_amazon`, `s3_oss`, `s3_other`, `ftp`, `sftp`, and `sls`. An HTTP receiver must return `2xx`, or Logs Uploader retries the batch. Target validation starts asynchronously — the first status is `in_progress`.</p>

<Tabs>
  <Tab title="Python SDK">
    ```python
    import os

    from gcore import Gcore

    client = Gcore()
    resource_id = int(os.environ["CDN_RESOURCE_ID"])

    # Step 1. Create a policy
    policy = client.cdn.logs_uploader.policies.create(
        name="cdn-json-export",
        fields=["cname", "code", "host"],
        include_empty_logs=False,
        rotate_interval_minutes=5,
        format_type="json",
    )
    print(policy.id, policy.name)

    # Step 2. Create an HTTP target
    target = client.cdn.logs_uploader.targets.create(
        name="http-collector",
        storage_type="http",
        config={
            "content_type": "json",
            "upload": {
                "url": "https://logs.example.com/cdn",
                "method": "POST",
            },
        },
    )
    print(target.id, target.storage_type)

    # Step 3. Create a configuration
    config = client.cdn.logs_uploader.configs.create(
        name="export-store",
        policy=policy.id,
        target=target.id,
        enabled=True,
        for_all_resources=False,
        resources=[resource_id],
    )
    print(config.id, config.enabled, config.policy, config.target)
    ```
