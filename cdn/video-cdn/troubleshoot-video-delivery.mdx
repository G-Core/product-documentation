Viewers often report video delivery problems that look like CDN failures. Start by separating CDN issues from origin issues, then match the symptom to the checks below.

## Separate CDN issues from origin issues

Before changing settings, identify where the problem is. Two checks usually answer this:

- **Browser DevTools (Network tab).** Play the video, open a failing request, and review the response status code (`200`, `403`, `404`, `504`) and the `Cache` response header (`HIT` or `MISS`). The [cache&nbsp;hit&nbsp;ratio](/cdn/video-cdn/improve-video-delivery-speed#how-to-check-your-cache-hit-ratio) section covers how to read these values.
- **CDN → Reports → Statistics.** Select the CDN resource and compare two reports:
  - **Response classes** — counts of `2xx`/`3xx`/`4xx`/`5xx` returned to viewers.
  - **Upstream response time** — the average time the CDN waited for the origin. A high or rising value points to an origin problem.

<Note>
A reliable test for any CDN-versus-origin question: request the failing URL directly from the origin, bypassing the CDN. If it also fails, the problem is on the origin side.
</Note>

## Issues viewers may report

### Video fails to start (403 / 410)

**What viewers see:** the video will not start or fails randomly — often for mobile users or viewers in a specific region — while it works for others on the same network. Player logs show `403 Forbidden` or `410 Gone`.

**Why it happens:** these resources use a [secure&nbsp;token](/cdn/video-cdn/secure-token). The token is tied to the viewer IP address. On mobile networks that use CGNAT, a public IP can change between requests within the same session, so a token signed for one IP is rejected when the next request arrives from a different one. A `410` means the token has expired (its TTL elapsed, or a viewer reused an old link).

**What to do:**

1. Confirm the status code in DevTools or raw logs: `403` = token rejected (often an IP mismatch), `410` = token expired.
2. For CGNAT or mobile audiences, change the IP truncation prefix to `/16` with support.
3. Apply correct TTL settings.
4. Verify the `expires` value is a future timestamp and that viewers are not loading cached pages with stale URLs.

Token rules are in [secure&nbsp;token](/cdn/video-cdn/secure-token) and [Secure&nbsp;Token&nbsp;setup](/cdn/cdn-resource-options/security/use-a-secure-token/configure-and-use-secure-token). Do not disable secure token to clear the errors — that removes content protection.

### Video buffers or is slow to start

**What viewers see:** the player spins or stalls before playback, segments load slowly, and the first view of a title is always slow.

**Why it happens:** the segment is not in the edge cache, so the CDN fetches it from the origin on demand (a cache MISS). This is expected for content with low or uneven traffic, where segments are evicted between views.

**What to do:**

1. In DevTools, check the `Cache` header on segment requests. Repeated `MISS` across page loads means a cold cache.
2. Confirm the cache hit ratio in **Reports → Statistics** and compare it against the [expected&nbsp;benchmarks](/cdn/video-cdn/improve-video-delivery-speed#what-cache-hit-ratio-to-expect).
3. [Enable&nbsp;origin&nbsp;shielding](/cdn/video-cdn/origin-shielding-for-video) so edge misses are absorbed by a shared shield instead of the origin.
4. Verify [cache&nbsp;TTLs](/cdn/cdn-resource-options/cache/specify-cache-lifetime-on-a-cdn-resource-or-origin) are long enough for segments, and [prefetch](/cdn/load-the-content-to-cdn-before-users-request-it) titles expected to be popular.

The full walkthrough is in [video&nbsp;delivery&nbsp;speed](/cdn/video-cdn/improve-video-delivery-speed).

### Live DASH 404 for future segments

**What viewers see:** intermittent `404 Not Found` on live MPEG-DASH segments (`.m4s`/`.mp4`), with the player stalling or rebuffering at the live edge. The same event delivered over HLS is unaffected.

**Why it happens:** a live DASH player works out which segment to request by combining the manifest timeline with the current wall-clock time. If the player asks for a segment that has not been generated and published to the origin yet — because the player clock is ahead of the packager, or the live-edge delay is too small — it requests a segment from the future. The CDN forwards the request to origin, origin has no such segment yet, and the viewer gets a `404`.

**What to do:**

1. Synchronize clocks. Run NTP on the encoder or packager, and add a `<UTCTiming>` element to the MPD so players sync to a time source instead of trusting the device clock.
2. Increase the live-edge delay so players stay safely behind the newest segment: raise `suggestedPresentationDelay` (and/or `timeShiftBufferDepth`) to roughly 2–3× the segment duration.
3. Verify the packager uploads each segment to origin before it announces that segment in the manifest — never advertise a segment that is not available yet.
4. Avoid caching the `404`: use a very short negative-cache TTL (or none) so a momentary miss does not persist after the segment becomes available.
5. To confirm it is timing and not the CDN, request the failing segment URL directly from origin at the moment of failure — if origin also returns `404`, the segment genuinely does not exist yet.

## Technical issues

These are the most common cases where monitoring systems report an issue.

### 504 timeout on newly published files

**What monitoring shows:** `504 Gateway Timeout` for videos uploaded or published recently, while older content on the same resource plays fine.

**Why it is the origin:** the CDN opens a connection to the origin, but the origin does not return response headers within the timeout. This usually means the new file is still transcoding, has not finished propagating in storage, or the origin is slow to serve content it has not prepared yet.

**What to do:**

1. Request the failing file directly from origin (bypass the CDN). If it also times out, the issue is confirmed origin-side.
2. Compare the file publish or upload time with the first failure. If failures cluster right after upload, let transcoding and storage propagation finish before sharing the link.
3. Confirm the origin returns the first byte well within a second; move heavy processing off the request path.
4. After publishing, [prefetch](/cdn/load-the-content-to-cdn-before-users-request-it) the file to warm the cache before viewers arrive.
5. Consider [Gcore&nbsp;Object&nbsp;Storage](/storage/use-storage-as-the-origin-for-your-cdn-resource) or [Video&nbsp;Streaming](/streaming/video-hosting/upload-a-video-and-embed-it-to-your-app) as the origin to remove this class of problem.

### 5xx errors during live events or traffic peaks

**What monitoring shows:** bursts of `5xx` errors when a popular live event starts or traffic spikes, which clear up once the event ends.

**Why it is the origin:** at peak, the origin (or an upstream CDN pulled from) cannot keep up and returns `5xx`, which the CDN passes through to viewers. Origins that rate-limit by IP can also throttle the CDN shield, producing the same symptom.

**What to do:**

1. In **Reports → Statistics**, line up **Response classes** (`5xx`) against **Upstream response time**. If upstream time rises with the errors, the origin is the bottleneck.
2. [Enable&nbsp;origin&nbsp;shielding](/cdn/video-cdn/origin-shielding-for-video) so thousands of concurrent edge misses collapse into a single origin request per object.
3. Provision origin capacity and bandwidth for the event ahead of time, and pre-warm popular content.
4. Remove or raise any origin rate limits that throttle CDN requests, and allowlist Gcore servers on the origin.
5. Use short but cacheable TTLs for live manifests so they can be served from cache instead of hitting origin on every refresh.

The full origin checklist is in [5xx&nbsp;server&nbsp;issues](/cdn/troubleshooting/5xx-error-how-to-solve-server-issues).

### The CDN will not cache the video

**What monitoring shows:** the cache hit ratio stays low and segments are served as `MISS` even with steady, repeated traffic — so it looks like the CDN is ignoring its cache.

**Why it is the origin:** the origin is sending response headers that tell the CDN not to cache — typically `Cache-Control: no-store`, `no-cache`, `private`, or `max-age=0`, but also `Set-Cookie` or an overly broad `Vary` header on video segments.

**What to do:**

1. Inspect the origin response headers: `curl -I https://cdn.example.com/path/to/segment.ts` and look at `Cache-Control`, `Expires`, `Pragma`, `Set-Cookie`, and `Vary`.
2. Fix the origin to send cacheable headers for video segments (a positive `max-age`, no `no-store`/`no-cache`, no per-request `Set-Cookie`).
3. If the origin cannot change, override the cache lifetime on the CDN resource so segments are cached regardless of origin headers — [Specify&nbsp;cache&nbsp;lifetime](/cdn/cdn-resource-options/cache/specify-cache-lifetime-on-a-cdn-resource-or-origin) covers that override.
4. [Purge&nbsp;the&nbsp;cache](/cdn/clear-cdn-resource-cache-by-url-pattern-or-all) and re-check the hit ratio after the change.

More detail is in [low&nbsp;hit&nbsp;ratio](/cdn/troubleshooting/cache-percentage-is-low-how-to-solve-the-issue).

## Contact support

If the relevant steps are complete and delivery is still failing, contact [Support](mailto:support@gcore.com) and include:

- The exact failing URL (the CDN segment or manifest URL, not the player page).
- The status code and `Cache` header from DevTools, and a screenshot of **Response classes** and **Upstream response time** from **Reports → Statistics**.
- Whether the content is live or VOD, and HLS or DASH.
- The affected region, ISP, and device type (mobile, desktop, Smart TV).
- The time window (in UTC) when the problem occurred.
- The output of `https://gcore.com/.well-known/cdn-debug/json` opened from the affected viewer network — [contact&nbsp;support&nbsp;details](/cdn/video-cdn/improve-video-delivery-speed#when-to-contact-support) explains what this snapshot contains.

CDN error code meanings are listed in [error&nbsp;status&nbsp;codes](/cdn/troubleshooting/gcore-error-status-codes).
