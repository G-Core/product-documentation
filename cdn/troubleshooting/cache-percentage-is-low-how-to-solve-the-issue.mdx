Cache hit ratio is the share of traffic served from CDN edge cache without an origin fetch. In the [Gcore Customer Portal](https://portal.gcore.com), open **CDN** > **Reports** > [Statistics](/cdn/view-statistics-of-a-cdn-resource), select the resource, then select **Cache hit ratio**.

<Frame>![Cache hit ratio report in Statistics](/images/docs/cdn/troubleshooting/cache-percentage-is-low-how-to-solve-the-issue/statistics-low-cache-hit-ratio.png)</Frame>

A higher ratio means more requests are served from cache, which lowers origin load and origin egress cost.

## Effect of a low ratio

A low ratio means many requests are proxied to the origin instead of being served from cache. A cached request is served from the edge back to the client. An uncached request adds an origin fetch, so latency rises with that extra hop.

## Checks for a low ratio

Work through the checks in order. Compare **Cache hit ratio** with **Traffic** and **Requests** in Statistics so a quiet period is not mistaken for a cache problem.

Complete Statistics data for a finished period is available at least two days after that period ends. Charts that are still in progress can show incomplete values. That reporting delay is separate from cache warm-up, which has no fixed duration.

Statistics marks cache hit rates below 60% in red on Overview as a visual highlight, not as a diagnostic cutoff. For this troubleshooting flow, start investigating when the ratio stays below about 80% after the cache has had time to fill, because that is where origin-bypass causes usually show up. The right target still depends on the workload.

1. Inspect caching headers with `curl -I`. Pin the request to one edge server, because consecutive requests in the same region can land on different servers and mix HIT and MISS.

```sh
curl -I cdn.example.com/assets/sample-image.png
```

<Accordion title="Request from one edge server">
Request the object that is not coming from cache and copy the `X-ID` header. That value identifies the edge server that handled the request.

Resolve the server IP:

```sh
nslookup {x-id}.fe.gc.onl
```

Use `dig` in place of `nslookup` if that is the local DNS tool. Then request the object from that IP:

```sh
curl -Ik -H "Host: cdn.example.com" "https://{ip-address}/assets/sample-image.png"
```

Compare `Cache-Control` and `Cache` with the table below.
</Accordion>

Focus on `Cache-Control` and `Cache` values that stop shared caching or force origin revalidation:

| Value | Meaning |
|---|---|
| Cache-Control: max-age=0 | The object is immediately stale, so the CDN revalidates with the origin before reuse. That extra origin contact lowers the hit ratio. In some workloads this value is intentional |
| Cache-Control: no-cache | Stored copies must be revalidated with the origin before reuse. On a shared CDN cache this often produces a MISS or revalidation on each request, which lowers the hit ratio. In some workloads this value is intentional |
| Cache-Control: no-store | The origin forbids storing the object, so the CDN cannot keep a reusable copy |
| Cache-Control: private | Shared caches must not store the object, so CDN edges fetch from the origin |
| Cache: MISS | The response came from the origin. Gcore CDN caches the object on the first request, so the first request is MISS and later requests for the same object on that edge are HIT |

Those headers show whether the origin or the CDN is preventing a HIT. Arbitrary custom request headers do not create unique cache objects by themselves. They affect caching only when they are part of the [cache key](/cdn/cdn-resource-options/cache/modify-cache-key), listed in `Vary`, or used by a bypass rule.

2. Open the resource **OPTIONS** tab and check [CDN caching](/cdn/cdn-resource-options/cache/specify-cache-lifetime-on-a-cdn-resource-or-origin) under **Cache**. The option must be enabled. For **CDN controlled**, do not set cache expiry to `0`. For **Origin controlled**, `max-age=0`, `no-cache`, `no-store`, or `private` on the origin reduce shared-cache HITs unless that behavior is required.

3. In **Cache**, review **Query string** and **Set-Cookie**. Query parameters are part of the request URL; `Set-Cookie` is a response header. When **Ignore query string** is off, each distinct query string is a separate cache object. When **Ignore Set-Cookie** is off, each `Set-Cookie` value is a separate cache object.

Enable **Ignore query string** or **Ignore Set-Cookie** only when those values do not change the response or personalize content. Ignoring a value that selects different content can serve the wrong cached object.

**Ignore query string** has three modes: **Ignore all**, **Ignore all except**, and **Ignore only**. Use **Ignore all except** or **Ignore only** when some parameters must remain in the cache key. Configuration is in the [query string](/cdn/cdn-resource-options/cache/ignore-the-set-cookie-or-query-string-parameters-when-caching-content-on-cdn-servers) article.

If delivery is slow but the cache hit ratio is healthy, use the [delivery speed](/cdn/troubleshooting/content-delivery-speed-is-low-how-to-solve-the-issue) checks instead.

## Other causes of a low ratio

After the header and option checks above, these traffic patterns can still keep the ratio low.

| Cause | Solution |
|---|---|
| Traffic started recently, so the cache is still filling | Wait for enough requests to populate edges. Warm-up duration depends on request volume, how often each object is requested, and cache lifetime. There is no fixed two-day warm-up |
| Statistics for a finished period still look incomplete | Complete Statistics data is available at least two days after the selected period ends. Live charts update during the period and can differ from later totals |
| Content is requested too rarely, so per-edge cache stays cold | Increase request volume, or use paid [Origin shielding](/cdn/cdn-resource-options/general/enable-and-configure-origin-shielding) to concentrate origin pulls. Low-traffic video is covered in [video delivery](/cdn/video-cdn/improve-video-delivery-speed) |
| Cache key modification adds extra request attributes | [Cache key modification](/cdn/cdn-resource-options/cache/modify-cache-key) supports `$request_uri`, `$scheme`, `$uri`, and `$http_x_cdn_real_host`. `$request_uri` keeps the query string in the key, and `$http_x_cdn_real_host` splits cache among aliases. Keep only the variables that must distinguish objects |
| Origin sends `Vary` for headers that do not change the response | A meaningful `Vary` value keeps different representations in separate cache objects, which is correct when content actually varies. Remove or narrow `Vary` on the origin only when the response does not vary by those request headers. [Response headers (hide)](/cdn/cdn-resource-options/http-headers/add-or-hide-response-headers#hide-response-headers) removes headers from responses to users and does not change how CDN cache processes `Vary` |
