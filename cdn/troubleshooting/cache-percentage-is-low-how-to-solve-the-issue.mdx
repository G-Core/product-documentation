Cache hit ratio is the share of traffic served from CDN edge cache without an origin fetch. In the [Gcore Customer Portal](https://portal.gcore.com), open **CDN** > **Reports** > [Statistics](/cdn/view-statistics-of-a-cdn-resource), select the resource, then select **Cache hit ratio**.

<Frame>![Cache hit ratio report in Statistics](/images/docs/cdn/troubleshooting/cache-percentage-is-low-how-to-solve-the-issue/statistics-low-cache-hit-ratio.png)</Frame>

A higher ratio means more requests are served from cache, which lowers origin load and origin egress cost.

## Effect of a low ratio

A low ratio means many requests are proxied to the origin instead of being served from cache. A cached request follows User → CDN edge → User. An uncached request follows User → CDN edge → Origin → CDN edge → User, so latency rises with the extra hop.

## Checks for a low ratio

Work through the checks in order. Compare **Cache hit ratio** with **Traffic** and **Requests** in Statistics so a quiet period is not mistaken for a cache problem. Below 80% is a useful starting threshold, while the right value depends on the workload.

1. Inspect caching headers with `curl -I`. Pin the request to one edge server, because consecutive requests in the same region can land on different servers and mix HIT and MISS.

```sh
curl -I cdn.example.com/assets/sample-image.png
```

<Accordion title="Request from one edge server">
Request the object that is not coming from cache and copy the `X-ID` header. That value identifies the edge server that handled the request.

Resolve the server IP:

```sh
nslookup {x-id}.fe.gc.onl
```

Use `dig` in place of `nslookup` if that is the local DNS tool. Then request the object from that IP:

```sh
curl -Ik -H "Host: cdn.example.com" "https://{ip-address}/assets/sample-image.png"
```

Compare `Cache-Control` and `Cache` with the table below.
</Accordion>

Focus on `Cache-Control` and `Cache` values that stop or split caching:

| Value | Meaning |
|---|---|
| Cache-Control: max-age=0 | The origin forbids CDN caching. This can drop the cache hit ratio. In some workloads this value is intentional. |
| Cache-Control: no-cache | The origin forbids CDN caching. This can drop the cache hit ratio. In some workloads this value is intentional. |
| Cache-Control: no-store | The origin forbids CDN caching. This can drop the cache hit ratio. In some workloads this value is intentional. |
| Cache-Control: private | Content is cached in the client browser only, not on CDN edges. A request that also sends custom `X-*` headers is treated as unique and is forwarded to the origin, similar to a cookie. |
| Cache: MISS | The response came from the origin. Gcore CDN caches the object on the first request, so the first request is MISS and later requests for the same object on that edge are HIT. |

Those headers show whether the origin or the CDN is preventing a HIT.

2. Open the resource **OPTIONS** tab and check [CDN caching](/cdn/cdn-resource-options/cache/specify-cache-lifetime-on-a-cdn-resource-or-origin) under **Cache**. The option must be enabled. For **CDN controlled**, do not set cache expiry to `0`. For **Origin controlled**, do not use `max-age=0`, `no-cache`, `no-store`, or `private` on the origin unless that is required.

3. If URLs differ only by query string or `Set-Cookie`, enable **Ignore query string** and **Ignore Set-Cookie** in **Cache**. When those options are off, each query string or cookie variant is stored as a separate object. Configuration is in the [query string](/cdn/cdn-resource-options/cache/ignore-the-set-cookie-or-query-string-parameters-when-caching-content-on-cdn-servers) article.

If delivery is slow but the cache hit ratio is healthy, use the [delivery speed](/cdn/troubleshooting/content-delivery-speed-is-low-how-to-solve-the-issue) checks instead.

## Causes of a low ratio

The table lists common causes and the matching fix.

| Cause | Solution |
|---|---|
| Traffic started less than two days ago, so the cache is still filling | Wait for traffic to populate edges. Around 48 hours after integration is typical, but the time depends on request patterns. Sending more traffic through CDN also fills the cache faster. |
| Content is requested too rarely, so per-edge cache stays cold | Increase request volume, or use paid [Origin shielding](/cdn/cdn-resource-options/general/enable-and-configure-origin-shielding) to concentrate origin pulls. Low-traffic video is covered in [video delivery](/cdn/video-cdn/improve-video-delivery-speed). |
| Cache-Control on the origin forbids CDN caching | Enable **CDN caching**. For **CDN controlled**, do not set cache expiry to `0`. For **Origin controlled**, do not send `max-age=0`, `no-cache`, `no-store`, or `private`. |
| Query strings or Set-Cookie make each request a new cache object | Enable **Ignore query string** and **Ignore Set-Cookie** so one object is stored regardless of parameters and cookies. |
| The origin sends Vary, so the same URL is cached in multiple variants | Change Vary on the origin, or use [Hide headers](/cdn/cdn-resource-options/http-headers/add-or-hide-response-headers#hide-response-headers). Enable **Response headers (hide)**, select **Hide only**, add **Vary**, then click **Save changes**. |
