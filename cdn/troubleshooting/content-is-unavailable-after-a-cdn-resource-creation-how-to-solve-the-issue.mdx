After a CDN resource is created, content can fail to load from the CDN hostname even when the origin still returns HTTP 200. Work through the origin check first, then the resource settings below.

## Origin HTTP response

Request a file that should be delivered through CDN from the origin. An HTTP 200 response means the origin is serving the object, so continue with the CDN settings. An HTTP 4xx or 5xx response means the origin is the problem, not the CDN.

Example origin request:

```text
http://example.com/image.png
```

`example.com` is the origin hostname, `http` is the origin protocol, and `image.png` is the object path.

## CDN resource settings

In the [Gcore Customer Portal](https://portal.gcore.com), navigate to **CDN** > **CDN resources** and open the resource. Each check below maps to one setting that commonly blocks delivery after creation.

### 1. Check the configuration of the personal domain

A missing or incorrect CNAME for the custom domain sends requests to the origin instead of the CDN. The Setup guide reports whether DNS is in place.

1. In resource settings, click **Setup guide**. If the wizard is not available, continue with the [Host&nbsp;header](#2-check-the-host-header-option) check.

<Frame>
  ![Setup guide in CDN resource settings](/images/docs/cdn/troubleshooting/content-is-unavailable-after-a-cdn-resource-creation-how-to-solve-the-issue/image1.png)
</Frame>

2. Click **Check DNS setup status**.

<Frame>
  ![Check DNS setup status in the Setup guide](/images/docs/cdn/troubleshooting/content-is-unavailable-after-a-cdn-resource-creation-how-to-solve-the-issue/image2.png)
</Frame>

If DNS is missing, this notification appears:

<Frame>
  ![DNS record has not been set up](/images/docs/cdn/troubleshooting/content-is-unavailable-after-a-cdn-resource-creation-how-to-solve-the-issue/image3.png)
</Frame>

If the notification appears, continue with step 3. If it does not, continue with the Host header check.

3. Open [DNS&nbsp;lookup](https://gcore.com/dev-tools/dns-lookup), enter the custom domain from the notification (`cdn.example.com` in the screenshot), select the resolvers, and click **Search**.

On the **CNAME** tab, a match with the Setup guide value means the record exists and DNS has not finished propagating. Repeat step 2 after 15 minutes.

If the result is **No records were found**, add the CNAME in [custom&nbsp;domain](/cdn/cdn-resource-options/general/create-and-set-a-custom-domain-for-the-content-delivery-via-cdn) settings.

4. Save DNS changes and wait for propagation. Updates usually finish within 15 minutes. A recent nameserver change can take up to 24 hours.

Request the object from the CDN hostname again. If the CNAME was the cause, delivery resumes.

### 2. Check the host header option

The [Host&nbsp;header](/cdn/cdn-resource-options/http-headers/configure-and-check-the-host-header) tells CDN nodes which origin hostname to request. When it does not match the origin, the origin cannot serve the object.

1. In resource settings, open **HTTP headers** and find **Host header**.

<Frame>
  ![Host header option in resource settings](/images/docs/cdn/troubleshooting/content-is-unavailable-after-a-cdn-resource-creation-how-to-solve-the-issue/image7.png)
</Frame>

2. Copy the Host header value.

3. In a terminal, run:

```sh
curl -H "Host: example.com" -I http://10.0.0.1/image.png
```

Replace `example.com` with the Host header value, `http` with the origin protocol, `10.0.0.1` with the origin IP, and `image.png` with the object path.

4. A 2xx response means the Host header is not the cause. Continue with [origin&nbsp;pull](#3-check-the-origin-pull-protocol-option).

A 4xx or 5xx response means the Host header is wrong. For a single origin, set the origin hostname in **Custom Host header**, then [purge&nbsp;cache](/cdn/clear-cdn-resource-cache-by-url-pattern-or-all). For several origins, each origin must accept that Host header. The header does not change automatically when the origin changes.

### 3. Check the origin pull protocol option

The [origin&nbsp;pull](/cdn/cdn-resource-options/general/specify-an-origin-and-the-origin-pull-protocol) protocol (HTTP, HTTPS, or both) is how CDN nodes fetch from the origin. The wrong protocol causes fetch errors or redirects.

1. Check the origin protocol in the browser address bar. A padlock means HTTPS (`https://example.com`).

<Frame>
  ![Browser padlock on an HTTPS origin](/images/docs/cdn/troubleshooting/content-is-unavailable-after-a-cdn-resource-creation-how-to-solve-the-issue/image8.png)
</Frame>

A **Not secure** label means HTTP (`http://example.com`).

<Frame>
  ![Not secure label on an HTTP origin](/images/docs/cdn/troubleshooting/content-is-unavailable-after-a-cdn-resource-creation-how-to-solve-the-issue/image9.png)
</Frame>

The origin can support both. Open `http://example.com` and `https://example.com` to confirm.

2. In resource settings, open **General** and find **Origin pull protocol**.

<Frame>
  ![Origin pull protocol in the General section](/images/docs/cdn/troubleshooting/content-is-unavailable-after-a-cdn-resource-creation-how-to-solve-the-issue/image10.png)
</Frame>

3. If the origin protocol and **Origin pull protocol** match, continue with the [SSL&nbsp;option](#4-check-the-ssl-option). If they differ, set **Origin pull protocol** to the origin protocol, save, and purge cache.

### 4. Check the SSL option

HTTPS delivery needs a certificate on the custom domain. A missing or invalid certificate blocks HTTPS or shows a browser trust warning.

<Frame>
  ![SSL settings in CDN resource settings](/images/docs/cdn/troubleshooting/content-is-unavailable-after-a-cdn-resource-creation-how-to-solve-the-issue/image11.png)
</Frame>

In **General**, open **SSL** and confirm **Enable HTTPS** is on.

<Frame>
  ![Enable HTTPS and certificate type in SSL settings](/images/docs/cdn/troubleshooting/content-is-unavailable-after-a-cdn-resource-creation-how-to-solve-the-issue/image12.png)
</Frame>

Certificate types are **Free Let's Encrypt certificate** and **Custom SSL certificate**. After issuing or adding a certificate, wait 15–30 minutes.

#### Free Let's Encrypt certificate

Let's Encrypt cannot issue a certificate until the custom domain CNAME exists. Complete the personal domain check first.

1. In resource settings, open **Rules**. If there are no rules, skip to the next certificate type.

<Frame>
  ![Rules section in CDN resource settings](/images/docs/cdn/troubleshooting/content-is-unavailable-after-a-cdn-resource-creation-how-to-solve-the-issue/image13.png)
</Frame>

2. Open each rule and review **Rule pattern**. Patterns that block Let's Encrypt validation include:

```text
/*
```

```text
((?!(jpeg|gif|png|pdf|jpg|css|js|woff|woff2|ttf)).)*$
```

Delete the rule or change the pattern, then wait for the next Let's Encrypt request. Full issuance steps are in [Let's&nbsp;Encrypt](/cdn/ssl-certificates/configure-lets-encrypt-certificate).

#### Personal SSL certificate

A third-party certificate must cover the custom domain, pass a trust check, and present a complete chain.

1. In a terminal, run:

```sh
curl -I https://cdn.example.com/image.png
```

Replace `cdn.example.com` with the custom domain and `image.png` with the object path.

A 2xx response means TLS handshake succeeded. Continue with the browser check.

This error means the certificate is self-signed, which cannot be used for CDN delivery:

```text
curl: (77) schannel: next InitializeSecurityContext failed: SEC_E_UNTRUSTED_ROOT (0x80090325)
```

Issue a certificate from a certificate authority and add it in [SSL&nbsp;certificates](/cdn/ssl-certificates/configure-your-own-ssl-certificate). Then purge cache.

2. In the browser, open an object on the CDN hostname. Click the padlock or **Not secure**, then open the certificate. Confirm it covers the custom domain, including a wildcard `*.example.com`, and is not expired.

<Frame>
  ![Certificate details in the browser](/images/docs/cdn/troubleshooting/content-is-unavailable-after-a-cdn-resource-creation-how-to-solve-the-issue/image14.png)
</Frame>

Renew or reissue the certificate if the name or dates are wrong.

3. On [SSL&nbsp;Labs](https://ssllabs.com/ssltest), enter the custom domain in **Hostname** and click **Submit**.

<Frame>
  ![SSL Labs test form](/images/docs/cdn/troubleshooting/content-is-unavailable-after-a-cdn-resource-creation-how-to-solve-the-issue/image15.png)
</Frame>

A rating of A+ with no chain issues means SSL is not the cause. Continue with [cache&nbsp;options](#5-check-the-cache-options).

<Frame>
  ![SSL Labs A+ rating](/images/docs/cdn/troubleshooting/content-is-unavailable-after-a-cdn-resource-creation-how-to-solve-the-issue/image16.png)
</Frame>

A B rating or chain issues means the certificate chain is incomplete.

<Frame>
  ![SSL Labs B rating with chain issues](/images/docs/cdn/troubleshooting/content-is-unavailable-after-a-cdn-resource-creation-how-to-solve-the-issue/image17.png)
</Frame>

In **CDN** > **SSL certificates**, delete the certificate and add it again.

### 5. Check the cache options

Wrong [CDN&nbsp;caching](/cdn/cdn-resource-options/cache/specify-cache-lifetime-on-a-cdn-resource-or-origin) settings produce a low cache hit ratio or slow delivery.

1. In **CDN**, open **Reports** > **Statistics**. Select the resource and the **Cache hit ratio** report.

<Frame>
  ![Cache hit ratio report in Statistics](/images/docs/cdn/troubleshooting/content-is-unavailable-after-a-cdn-resource-creation-how-to-solve-the-issue/image19.png)
</Frame>

A cache hit ratio below 60 percent means little traffic is served from cache.

A new resource needs about two days and enough client traffic to warm cache. Idle cache can expire in 36 hours regardless of settings. If the ratio is above 60 percent and load time is acceptable, continue with [purge](#6-check-the-purge-option).

2. Request a CDN object and inspect `Cache` and `Cache-Control`. These values usually mean caching is misconfigured:

   - `Cache-Control: max-age=0`
   - `Cache-Control: private`
   - `Cache-Control: no-cache`
   - `Cache: MISS`

3. In resource settings, open **Cache** > **CDN caching** and set the policy for the origin.

<Frame>
  ![CDN caching option](/images/docs/cdn/troubleshooting/content-is-unavailable-after-a-cdn-resource-creation-how-to-solve-the-issue/image20.png)
</Frame>

4. If objects vary only by query string or `Set-Cookie`, enable [Ignore&nbsp;Query&nbsp;String](/cdn/cdn-resource-options/cache/ignore-the-set-cookie-or-query-string-parameters-when-caching-content-on-cdn-servers) and Ignore Set-Cookie so those variants share one cache key.

<Frame>
  ![Query string and Set-Cookie cache options](/images/docs/cdn/troubleshooting/content-is-unavailable-after-a-cdn-resource-creation-how-to-solve-the-issue/image21.png)
</Frame>

### 6. Check the purge option

A bad purge leaves users on a stale or wrong object, which means the CDN copy no longer matches the origin.

1. Wait 15 minutes after a purge so every edge finishes.

2. Request the same object from the CDN hostname and from the origin:

```sh
curl -I cdn.example.com/image.png
curl -H "Host: example.com" -I http://10.0.0.1/image.png
```

3. Compare `Content-Length`, `ETag`, and `X-Cached-Since`. Mismatched size or ETag, or an old `X-Cached-Since` date, means the purge did not apply. Matching values mean the purge succeeded.

4. Purge again. For selective purge, test the path pattern in a [regex&nbsp;tester](https://regex101.com). Put the purge pattern on the first line and the object URL below. **No matches** means the pattern is wrong. Correct it and purge again.

If delivery still fails after these checks, contact [Gcore&nbsp;Support](mailto:support@gcore.com).
