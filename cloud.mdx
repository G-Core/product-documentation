<a href="https://gcore.com/cloud" target="_blank" rel="noopener noreferrer">Edge&nbsp;Cloud</a> runs workloads on infrastructure that Gcore operates. Those workloads run as Virtual Instances or Bare Metal servers, or on managed platforms for containers and databases, with storage and networking around them.

## Run a server

Place the workload on shared hardware or on a physical machine reserved for one account.

<CardGroup cols={2}>

<Card title="Virtual Instances" href="/cloud/virtual-instances/create-an-instance">
Run a virtual server on shared physical hardware, with control over its operating system and installed software. Choose the instance type to match the workload's CPU, memory, and performance requirements.
</Card>

<Card title="Bare Metal" href="/cloud/bare-metal-servers/create-a-bare-metal-server">
Run workloads on a dedicated physical server without sharing its hardware with other accounts. Connect the server to private networks alongside Virtual Instances and other Cloud resources.
</Card>

</CardGroup>

A [GPU](/cloud/virtual-instances/types-of-virtual-machines#gpu) type is one Virtual Instance with a graphics accelerator. [GPU&nbsp;Cloud](/edge-ai/ai-infrastructure/about-gpu-cloud) is a dedicated cluster of servers, with multiple GPUs on each server.

## Run an application

Each service leaves a different share of the work with the account.

<CardGroup cols={2}>

<Card title="Managed Kubernetes" href="/cloud/kubernetes/about-gcore-kubernetes">
Run containerized workloads on Kubernetes clusters backed by Virtual Instances or Bare Metal servers. Gcore manages the control plane, while the account controls node pools and workloads.
</Card>

<Card title="Container" href="/cloud/caas">
Deploy a container image without setting up a Kubernetes cluster or managing Virtual Machines. Gcore handles the underlying infrastructure and scales the container as needed.
</Card>

</CardGroup>

Container images for Managed Kubernetes, Container as a Service, and Everywhere Inference are stored in [Container&nbsp;Registry](/cloud/container-registry). A disk image for a Virtual Instance is a separate object.

## Store data

Decide where the workload's files live.

<CardGroup cols={3}>

<Card title="Volumes" href="/cloud/virtual-instances/volumes/about-volumes">
Use volumes to store a Virtual Instance's operating system and application data.
</Card>

<Card title="Images" href="/cloud/images/about-images">
An image is a copy of a disk. Creating a Virtual Instance copies that image onto the boot volume.
</Card>

<Card title="File shares" href="/cloud/file-shares/about-file-shares">
Share files between Virtual Instances, Bare Metal servers, and Kubernetes pods.
</Card>

</CardGroup>

## Connect servers

Give servers a path to each other and a path from the internet.

<CardGroup cols={2}>

<Card title="Networks" href="/cloud/networking/create-and-manage-a-network">
Use private networks for internal communication, public interfaces for internet access, or dedicated networks to assign Bare Metal servers a separate pool of public IP addresses.
</Card>

<Card title="Load Balancers" href="/cloud/networking/create-and-configure-a-load-balancer">
Distribute incoming requests across multiple backend servers instead of sending all traffic to one. Configure listeners, backend pools, and health checks to control how requests are routed.
</Card>

</CardGroup>

After connecting Cloud resources, configure how they can be reached and which traffic they accept:

- **[Control&nbsp;network&nbsp;access](/cloud/networking/add-and-configure-a-firewall):** Configure security groups to allow or restrict traffic to Virtual Instances.
- **[Choose&nbsp;IP&nbsp;addresses](/cloud/networking/ip-address/difference-between-virtual-floating-and-reserved-ip-addresses):** Compare floating, reserved, and virtual IP addresses to find the right addressing option.
- **[Enable&nbsp;HTTPS](/cloud/secrets-manager/upload-a-pkcs12-file):** Upload a TLS certificate to Secrets Manager for use with an HTTPS load balancer.

## Databases

Keep relational data on a server that Gcore operates.

<Card title="Managed PostgreSQL" href="/cloud/managed-database-postgresql">
Run PostgreSQL databases without maintaining the database server. Gcore handles the underlying infrastructure, with optional replicas to improve availability if the primary server fails.
</Card>

## Monitoring

Monitor Cloud resources and investigate performance issues using metrics and logs.

- [Monitoring](/cloud/virtual-instances/monitor-load-and-performance-of-your-instance) shows CPU, memory, network, and disk usage to help identify performance problems with Virtual Instances.
- [Managed&nbsp;Logging](/cloud/logging-as-a-service/about-logging-as-a-service) collects logs from multiple servers in one place for troubleshooting and incident investigation.

## Access and cost

Organize Cloud resources, manage access permissions, and keep track of resource limits and costs.

- [Create&nbsp;and&nbsp;manage&nbsp;projects](/cloud/getting-started/projects/create-a-project) to separate workloads and environments.
- [Use&nbsp;tags](/cloud/tags) to identify and organize resources.
- [Configure&nbsp;user&nbsp;roles](/cloud/getting-started/projects/users/user-roles-and-rights) to control who can access and manage resources.
- [Check&nbsp;quotas&nbsp;and&nbsp;request&nbsp;increases](/cloud/getting-started/request-a-quota-increase) when more capacity is needed.
- [Review&nbsp;billing](/cloud/billing) to understand how Cloud resources are charged.
