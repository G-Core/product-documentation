title: Protect a TCP service
sidebarTitle: Quick start
description: Protect a TCP service on port 80 by routing connections through a Gcore protected IP address.
---

This quick start shows how to protect a TCP service on port 80 with Gcore Edge Proxy. You'll create a proxy profile using the Generic TCP Server policy, wait for its protected IP address to become ready, and verify that connections reach your application through it.

<Info>
You need an [API&nbsp;token](/account-settings/api-tokens), `curl`, and `jq`. Run the commands in the same shell because later steps use variables set by earlier ones. If a command reports an error, resolve it before moving to the next step.
</Info>

<Steps>
<Step title="Prepare the origin">

The origin is the server that Edge Proxy will forward legitimate connections to. It must be reachable through a public IPv4 address or domain name, and the application must accept TCP connections on port 80.

Your account must also have Edge Proxy Active. Check the service status in your [dashboard](/account-settings/account/services). If it is inactive, start it from the [service&nbsp;menu](/account-settings/billing/trial-conditions) or contact Gcore Support to resume a stopped service.

Allow only the Gcore edge IP addresses listed in [Restrict&nbsp;access](/edge-proxy/setup-and-configuration#restrict-access-to-the-origin) to reach the origin on port 80, and block all other sources. Otherwise, attackers can reach the origin directly and bypass Edge Proxy, and traffic may pass through Edge Proxy but fail to reach your application.

Set your API token and the origin address for the following commands:

```bash
export GCORE_API_KEY="{YOUR_API_KEY}"
export EDGE_PROXY_ORIGIN="{YOUR_ORIGIN_HOST}"
```

</Step>
<Step title="Select a template and policy">

A profile can use only policies from its selected template. For an ordinary TCP service, use the Generic TCP Server policy (`tcp-server`) from the account's default template, identified by `is_default` in the [template&nbsp;list](/api-reference/edge-proxy/proxy-templates/list-proxy-templates).

The commands find that template and policy, save their IDs as `TEMPLATE_ID` and `POLICY_ID`, and display the selected entries:

```bash
unset TEMPLATE_ID POLICY_ID
template_json=$(curl --fail --silent --show-error \
  "https://api.gcore.com/security/edgeproxy/v3/templates?limit=100" \
  -H "Authorization: APIKey $GCORE_API_KEY")
TEMPLATE_ID=$(printf '%s' "$template_json" | jq -r '.results | map(select(.is_default == true)) | .[0].id // empty')
POLICY_ID=$(printf '%s' "$template_json" | jq -r '.results | map(select(.is_default == true)) | .[0].policies | map(select(.id == "tcp-server")) | .[0].id // empty')
if [ -z "$TEMPLATE_ID" ] || [ -z "$POLICY_ID" ]; then
  printf '%s\n' "The default template or Generic TCP Server policy was not returned." >&2
else
  export TEMPLATE_ID POLICY_ID
  printf '%s\n' "$template_json" \
    | jq '.results[] | select(.is_default == true) | {id, policies: [.policies[] | select(.id == "tcp-server") | {id, name}]}'
fi
```

For example, the selected entries may look like this (your template ID may differ):

```json
{
  "id": 1,
  "policies": [
    {
      "id": "tcp-server",
      "name": "Generic TCP Server"
    }
  ]
}
```

If the template or policy is not found, do not continue until you have valid IDs for both.

</Step>
<Step title="Create the profile">

Now create a profile that links your origin to a protected IP address and applies the selected policy to TCP port 80. The [Create&nbsp;proxy&nbsp;profile](/api-reference/edge-proxy/proxy-profiles/create-proxy-profile) API takes these settings in one request:

| Parameter | Value in this example |
| --- | --- |
| `name` | `edge-proxy-profile` (a name from 1 to 60 characters) |
| `origin_host` | The address stored in `EDGE_PROXY_ORIGIN` |
| `template_id` | The template ID stored in `TEMPLATE_ID` |
| `rules` | The `tcp-server` policy with a TCP port 80 mapping |

Leave `protected_ip_address` unset so Gcore assigns it automatically. In this quick start, both the protected IP and the origin use port 80, so the mapping does not need `outbound_port`.

If your application listens on port 8080 instead, the mapping would look like this:

```json
{
  "protocol": "tcp",
  "port": 80,
  "outbound_port": 8080
}
```

To use this alternative, change the mapping in the request below, allow the same Gcore edge IP addresses to reach port 8080, and block other sources on that port. The following command uses port 80 on both sides.

```bash
if [ -z "${TEMPLATE_ID:-}" ] || [ -z "${POLICY_ID:-}" ]; then
  printf '%s\n' "Select a valid template and policy before creating the profile." >&2
else
  body=$(jq -n \
    --arg name "edge-proxy-profile" \
    --arg origin "$EDGE_PROXY_ORIGIN" \
    --argjson template_id "$TEMPLATE_ID" \
    --arg policy "$POLICY_ID" \
    '{name:$name, origin_host:$origin, template_id:$template_id, rules:[{policy:$policy, mappings:[{protocol:"tcp", port:80}]}]}')
  unset PROFILE_ID
  if create_json=$(curl --fail --silent --show-error \
    --request POST "https://api.gcore.com/security/edgeproxy/v3/profiles" \
    -H "Authorization: APIKey $GCORE_API_KEY" \
    -H "Content-Type: application/json" \
    --data "$body"); then
    printf '%s\n' "$create_json" | jq '{id, status, is_processing, is_error, protected_ip_address, error_details}'
    PROFILE_ID=$(printf '%s' "$create_json" | jq -r '.id // empty')
    if [ -n "$PROFILE_ID" ]; then
      export PROFILE_ID
    else
      printf '%s\n' "The response did not contain a profile ID." >&2
    fi
  fi
fi
```

A successful request returns HTTP 201 with a profile ID and an assigned protected IP address. Deployment has only just started, so the profile is still `INACTIVE` and `is_processing` is `true`:

```json
{
  "id": 42,
  "status": "INACTIVE",
  "is_processing": true,
  "is_error": false,
  "error_details": null,
  "protected_ip_address": "203.0.113.20"
}
```

If the API returns `400`, possible causes include an inactive Edge Proxy service, no available protected IP addresses, an origin already assigned to an active profile, or a profile limit that has been reached.

</Step>
<Step title="Wait for deployment">

Receiving a protected IP address does not mean it can accept connections yet. Edge Proxy must first deploy the profile across its edge network. The following command checks the profile status repeatedly and saves the address as `PROTECTED_IP` only after the deployment succeeds.

```bash
if [ -z "${PROFILE_ID:-}" ]; then
  printf '%s\n' "Create the profile before checking deployment." >&2
else
  unset PROTECTED_IP
  processing="true"
  for _ in $(seq 1 36); do
    if ! profile_json=$(curl --fail --silent --show-error \
      "https://api.gcore.com/security/edgeproxy/v3/profiles/$PROFILE_ID" \
      -H "Authorization: APIKey $GCORE_API_KEY"); then
      printf '%s\n' "Could not read the profile status." >&2
      break
    fi
    processing=$(printf '%s' "$profile_json" | jq -r '.is_processing')
    if [ "$processing" = "false" ]; then
      break
    fi
    sleep 5
  done
  if [ "$processing" != "false" ]; then
    printf '%s\n' "Deployment was not confirmed ready. Check the profile again before continuing." >&2
  else
    status=$(printf '%s' "$profile_json" | jq -r '.status')
    is_error=$(printf '%s' "$profile_json" | jq -r '.is_error')
    protected_ip=$(printf '%s' "$profile_json" | jq -r '.protected_ip_address')
    if [ "$status" != "ACTIVE" ] || [ "$is_error" != "false" ] || [ -z "$protected_ip" ] || [ "$protected_ip" = "null" ]; then
      printf '%s\n' "$profile_json" | jq '{id, status, is_processing, is_error, error_details, protected_ip_address}'
      printf '%s\n' "The profile is not ready for client connections." >&2
    else
      export PROTECTED_IP="$protected_ip"
      printf '%s\n' "$profile_json" | jq '{id, status, is_processing, is_error, protected_ip_address, error_details}'
    fi
  fi
fi
```

When deployment succeeds, `status` becomes `ACTIVE`, `is_processing` is `false`, and `is_error` is `false`. A new profile reaches this state automatically; you do not need to call Activate.

```json
{
  "id": 42,
  "status": "ACTIVE",
  "is_processing": false,
  "is_error": false,
  "error_details": null,
  "protected_ip_address": "203.0.113.20"
}
```

If `is_error` is `true`, check `error_details` to identify the failure. Do not direct clients to the protected IP until all three readiness conditions are met and `PROTECTED_IP` has been set.

</Step>
<Step title="Direct clients to the protected IP">

Once the profile is ready, clients can connect to `PROTECTED_IP` on TCP port 80 instead of connecting directly to the origin. If they use a domain name, point its DNS A record (which maps the name to an IPv4 address) to the protected IP instead of the origin.

Connections sent directly to the origin still bypass Edge Proxy filtering.

</Step>
<Step title="Verify the connection">

Connect to the protected IP on port 80 using your application's normal client. A successful test returns the response you expect from the application, but now through Edge Proxy rather than directly from the origin.

If your TCP service uses HTTP and accepts requests sent to its IP address, you can check it with curl:

```bash
curl --fail --silent --show-error "http://$PROTECTED_IP/"
```

If the HTTP application selects a site based on the hostname, include that name in the Host header:

```bash
curl --fail --silent --show-error \
  --header "Host: {YOUR_HOSTNAME}" \
  "http://$PROTECTED_IP/"
```

If the connection fails even though the profile is `ACTIVE`, check that the origin allows traffic from the Gcore edge IP addresses and that the filtering policy matches your application. For hostname-based HTTP services, also check that the application recognizes the Host value. See [Connection&nbsp;failures](/edge-proxy/faqs-and-troubleshooting) for troubleshooting steps.

</Step>
</Steps>
