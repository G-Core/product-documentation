<p>Healthchecks keep a site or application available when one or more servers go down. This feature monitors server availability and excludes non-working IPs from DNS responses when issues occur. As a result, traffic is redirected from the problematic server to a working one, and the resource stays available for all users.</p>

<Accordion title="Example of how Healthchecks works">
This feature is especially important for business areas where the loss of availability means the loss of customers. Consider an online store that serves Europe and the US. The site runs on two servers — a European one and an American one — with Geobalancing routing visitors to the closest server. Customers from Paris and Barcelona are balanced to the European server, while customers from Vancouver and Chicago are balanced to the American one.


<Frame>![Healthchecks scheme: both servers work](/images/docs/dns/dns-failover/configure-and-use-dns-failover/health-checks-1.png)</Frame>



If the European server crashes, visitors balanced to it receive an error instead of the site. While the server is being fixed, customers visit a competitor's site instead.


<Frame>![Healthchecks scheme: one server is broken](/images/docs/dns/dns-failover/configure-and-use-dns-failover/health-checks-2.png)</Frame>



With Healthchecks enabled, the next time the European server crashes, Healthchecks tells the DNS server not to include the unavailable IP in responses. All requests are directed to the American server, so the web application stays available — customers can continue making purchases without noticing the outage.


<Frame>![Healthchecks scheme: redirecting requests to a working server](/images/docs/dns/dns-failover/configure-and-use-dns-failover/health-checks-3.png)</Frame>



When the European server recovers, Healthchecks detects that and restores its IP in DNS responses for users in Europe.
</Accordion>


## Healthchecks mechanism

<p>Healthchecks continuously poll configured records and update DNS responses based on server availability:</p>

<Steps>
  <Step title="Healthchecks send requests to servers">
  DNS Healthchecks sends requests to servers to check their availability. Configure request settings — protocol, frequency, and others — in the Gcore Customer Portal after the feature is enabled.

  A sample configuration:

  * Protocol: ICMP
  * Frequency: 1 minute
  * Timeout: 10 seconds

  With this configuration, DNS Healthchecks sends requests to web servers via ICMP every 60 seconds.

  <Frame>![Health Checks scheme](/images/docs/dns/dns-failover/configure-and-use-dns-failover/health-checks-4.png)</Frame>
  </Step>
  <Step title="Healthchecks classify servers">
  A server is marked available when it responds successfully from at least 85% of Gcore DNS locations. It is marked unavailable when successful responses drop below 20% of locations. The gap between these thresholds prevents status flapping — a server must fully recover above 85% before being restored to DNS responses.

  <Frame>![Health Checks scheme](/images/docs/dns/dns-failover/configure-and-use-dns-failover/health-checks-5.png)</Frame>
  </Step>
  <Step title="Unavailable records are excluded from DNS responses">
  If a web server is unavailable, Healthchecks marks the corresponding record as unavailable, and the DNS server excludes it from responses.

  <Info>
  If all Healthchecks fail, their A records will be included in the DNS response, while still adhering to other filters like _geo county_ or _first_n_.
  </Info>

  <Frame>![Health Checks scheme](/images/docs/dns/dns-failover/configure-and-use-dns-failover/health-checks-6.png)</Frame>
  </Step>
  <Step title="DNS responses include only available servers">
  The DNS server removes the unavailable record from responses. Subsequent DNS queries return only available records, so clients resolve the hostname to working servers.

  The load balancing mechanism decides which server responds. By default, DNS Healthchecks use round-robin, but a custom mechanism can be configured. [Dynamic&nbsp;response](/dns/dns-records/configure-weight-balancing-and-geobalancing) covers the available load balancing options.

  <Frame>![Health Checks scheme](/images/docs/dns/dns-failover/configure-and-use-dns-failover/health-checks-7.png)</Frame>
  </Step>
  <Step title="Recovered servers are restored to DNS responses">
  Healthchecks keep sending requests to web servers. When the web server becomes available and responds, the feature sends the appropriate update to the DNS server, and the web server goes back online for end-users.

  <Frame>![Health Checks scheme](/images/docs/dns/dns-failover/configure-and-use-dns-failover/health-checks-8.png)</Frame>

  <Frame>![Health Checks scheme](/images/docs/dns/dns-failover/configure-and-use-dns-failover/health-checks-9.png)</Frame>
  </Step>
</Steps>



## Configure healthchecks

<Caution>
<p>Healthchecks are available only in advanced interface mode and apply to A, AAAA, and CNAME records only.</p>
</Caution>

<Steps>
  <Step title="Open the DNS section">
  In the [Gcore Customer Portal](https://portal.gcore.com), navigate to **DNS**.
  </Step>
  <Step title="Open the DNS zone">
  Click the domain name of the DNS zone where Healthchecks will be configured.

  <Frame>![Open a DNS zone](/images/docs/dns/dns-failover/configure-and-use-dns-failover/healthchecks-08.png)</Frame>
  </Step>
  <Step title="Open the record for editing">
  Click the three-dot icon and click **Edit record** in the row of the A, AAAA, or CNAME record.

  <Frame>![Open a Records list/Edit record set page](/images/docs/dns/dns-failover/configure-and-use-dns-failover/healthchecks-10.png)</Frame>
  </Step>
  <Step title="Enable Dynamic response">
  Enable the **Dynamic response** toggle.
  </Step>
  <Step title="Add a Healthcheck picker">
  In the left column, select the **Healthcheck** picker.

  <Frame>![Select a Healthchecks picker](/images/docs/dns/dns-failover/configure-and-use-dns-failover/healthchecks-20.png)</Frame>
  </Step>
  <Step title="Open picker settings">
  Click the edit icon when the picker is added to the left column.

  A pop-up will open. The settings differ depending on the protocol: TCP/UDP, ICMP, or HTTP. Select the relevant tab below to complete configuration.

  <Tabs>
    <Tab title="TCP/UDP">
      <Frame>![Configure a Healthchecks picker: TCP or UDP](/images/docs/dns/dns-failover/configure-and-use-dns-failover/healthchecks-30.png)</Frame>

      1. Under "Protocol", select **TCP** or **UDP**.
      2. In the "Port" field, specify the connection port (e.g., 80 or 443).
      3. In the "Check Frequency" field, select the interval of checks from the list.
      4. In the "Timeout" field, set the time within which the web servers should give the response before being considered down.
      5. (Optional) In the "Command" field, enter the text that will be sent to the host as plain text, for instance: `GET / HTTP/1.1\n\n`.
      6. (Optional) In the "Expected content regexp" field, enter a regular expression that matches the response body or leave it blank.
      7. Click **Save**.
    </Tab>
    <Tab title="ICMP">
      <Frame>![Configure a Healthchecks picker: ICMP](/images/docs/dns/dns-failover/configure-and-use-dns-failover/healthchecks-40.png)</Frame>

      1. Under "Protocol", select **ICMP**.
      2. In the "Check Frequency" field, select the interval of checks from the list.
      3. In the "Timeout" field, set the time within which the web servers should give the response before being considered down.
      4. Click **Save**.
    </Tab>
    <Tab title="HTTP">
      <Frame>![Configure a Healthchecks picker: HTTP](/images/docs/dns/dns-failover/configure-and-use-dns-failover/healthchecks-50.png)</Frame>

      1. In the "Protocol" block, select **HTTP**.
      2. In the "Port" field, specify the connection port (e.g., 80 or 443).
      3. In the "Check Frequency" field, select the interval of checks from the list.
      4. In the "Timeout" field, set the time within which the web servers should give the response before being considered down.
      5. (Optional) In the "Host" field, specify a value of the Host header to be passed during the HTTP request.
      6. In the **Request URL** field, enter the URL that will be requested for checks.
      7. In the **Request Method** block, select the method for checking requests; e.g., GET.
      8. In the "Use TLS" block, select whether TLS should be used.
      9. In the "HTTP status code" field, put the expected HTTP response code or leave it blank if any response is acceptable.
      10. (Optional) In the "Expected content regexp" field, enter a regular expression that matches the response body or leave it blank.
      11. Click **Save**.
    </Tab>
  </Tabs>
  </Step>
</Steps>

<p>Healthchecks begin monitoring the configured address on the next check interval. If the server is unreachable, its record is excluded from DNS responses automatically and restored once it recovers. Recent monitoring events are available in the logs.</p>

## Enable backup metadata

<p>Backup metadata keeps designated records out of DNS responses as long as at least one non-backup record is healthy. When all primary records fail, backup records take over automatically.</p>

<p>In the record settings, open the metadata dropdown for the record that should serve as the backup, select **backup**, and enable it.</p>

<Frame>![Configure backup metadata](/images/docs/dns/dns-failover/configure-and-use-dns-failover/healthchecks-60.png)</Frame>

<p>By default, DNS Healthchecks use round-robin balancing. [Dynamic&nbsp;response](/dns/dns-records/configure-weight-balancing-and-geobalancing) covers the options for configuring how requests are distributed among available servers.</p>

<p>Healthchecks are configured at the RRset level. The `meta.failover` object defines the check protocol and parameters; the `healthcheck` picker activates monitoring. Individual records that act as backup — used only when all primary records fail — carry `meta.backup: true` at the record level.</p>

<Info>
An [API&nbsp;token](/account-settings/api-tokens) is required. Healthchecks apply to A, AAAA, and CNAME records only.
</Info>

<p>Export these variables:</p>

```bash
export GCORE_API_KEY="{YOUR_API_KEY}"
export ZONE_NAME="{YOUR_ZONE_NAME}"
export RECORD_NAME="{RECORD_FQDN}"
```

<p>`RECORD_NAME` is the fully qualified domain name (FQDN) of the record. For an apex record it matches `ZONE_NAME`; for a subdomain it is the full FQDN, such as `www.company.com`.</p>

## Configure healthchecks

<p>This code creates an A record with HTTP health monitoring and a backup record that takes over when the primary fails. The `meta.failover` object sits at the RRset level and applies to all records; `meta.backup: true` marks a single record as the failover target. The `first_n` picker limits each DNS response to one available record.</p>

<Tabs>
  <Tab title="Python SDK">
```python
import os
from gcore import Gcore

client = Gcore()

rrset = client.dns.zones.rrsets.create(
    "A",
    zone_name=os.environ["ZONE_NAME"],
    rrset_name=os.environ["RECORD_NAME"],
    resource_records=[
        {"content": ["1.2.3.4"]},
        {"content": ["5.6.7.8"], "meta": {"backup": True}},
    ],
    meta={
        "failover": {
            "protocol": "HTTP",
            "port": 80,
            "frequency": 300,
            "timeout": 10,
            "method": "GET",
            "url": "/health",
            "tls": False,
            "http_status_code": 200,
        }
    },
    pickers=[
        {"type": "healthcheck"},
        {"type": "first_n", "limit": 1},
    ],
    ttl=300,
)
print(rrset.name, rrset.pickers)
```
  </Tab>
  <Tab title="Go SDK">
```go
package main

import (
    "context"
    "fmt"
    "os"

    gcore "github.com/G-Core/gcore-go"
    "github.com/G-Core/gcore-go/dns"
)

func main() {
    client := gcore.NewClient()
    ctx := context.Background()

    rrset, err := client.DNS.Zones.Rrsets.New(ctx, "A", dns.ZoneRrsetNewParams{
        ZoneName:  os.Getenv("ZONE_NAME"),
        RrsetName: os.Getenv("RECORD_NAME"),
        ResourceRecords: []dns.ZoneRrsetNewParamsResourceRecord{
            {Content: []any{"1.2.3.4"}},
            {Content: []any{"5.6.7.8"}, Meta: map[string]any{"backup": true}},
        },
        Meta: map[string]any{
            "failover": map[string]any{
                "protocol":         "HTTP",
                "port":             80,
                "frequency":        300,
                "timeout":          10,
                "method":           "GET",
                "url":              "/health",
                "tls":              false,
                "http_status_code": 200,
            },
        },
        Pickers: []dns.ZoneRrsetNewParamsPicker{
            {Type: "healthcheck"},
            {Type: "first_n", Limit: gcore.Int(1)},
        },
        Ttl: gcore.Int(300),
    })
    if err != nil {
        panic(err)
    }
    fmt.Println(rrset.Name, rrset.Pickers)
}
```
  </Tab>

```bash
    },

```

| --- | --- |

## Failover logs

<p>Retrieve recent monitoring events for an RRset. Each log entry reports the record address, the action taken (`activated` or `deactivated`), and the Unix timestamp.</p>

<Tabs>
  <Tab title="Python SDK">
```python
import os
from gcore import Gcore

client = Gcore()

logs = client.dns.zones.rrsets.get_failover_logs(
    "A",
    zone_name=os.environ["ZONE_NAME"],
    rrset_name=os.environ["RECORD_NAME"],
)
print(logs.total_amount, logs.log)
```
  </Tab>
  <Tab title="Go SDK">
```go
package main

import (
    "context"
    "fmt"
    "os"

    gcore "github.com/G-Core/gcore-go"
    "github.com/G-Core/gcore-go/dns"
)

func main() {
    client := gcore.NewClient()
    ctx := context.Background()

    logs, err := client.DNS.Zones.Rrsets.GetFailoverLogs(ctx, "A", dns.ZoneRrsetGetFailoverLogsParams{
        ZoneName:  os.Getenv("ZONE_NAME"),
        RrsetName: os.Getenv("RECORD_NAME"),
    })
    if err != nil {
        panic(err)
    }
    fmt.Println(logs.TotalAmount, logs.Log)
}
```
