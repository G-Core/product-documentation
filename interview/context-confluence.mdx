## CDN / Custom error pages — Feature overview

**Last updated:** 3 weeks ago by alex.v
**Status:** Internal — in limited rollout

---

### What it does

Custom error pages allow CDN resource owners to replace the default Gcore error response with their own HTML page. When the CDN encounters a configured error code, it fetches the customer's page from the specified URL and serves it to the end user.

### Supported error codes (current release)

The initial release supports the following codes:

- 400 Bad Request
- 401 Unauthorized
- 403 Forbidden
- 404 Not Found
- 500 Internal Server Error
- 502 Bad Gateway
- 503 Service Unavailable
- 504 Gateway Timeout

Full 4xx/5xx support is planned for Q2 2027.

> **INTERNAL NOTE:** The codes above represent the planned full list. The *current* release (v2.14.1) only ships with 404, 503, and 429. The rest will be enabled incrementally. Do not communicate the full list externally until each code is live.

### Availability

> **INTERNAL — do not include in public documentation.**
>
> Feature is currently in limited availability. The feature flag (`cdn_custom_error_pages_enabled`) is off by default. Support can enable it manually per account on request. Full GA is planned for Q1 2027. Do not confirm availability to customers who ask proactively — route to the account manager.

### Pricing

> **INTERNAL — do not include in public documentation.**
>
> Custom error pages are included at no additional charge on Start, Pro, and Pro+ plans. On the PAYG plan, error page responses above 10,000 per calendar month are billed at €0.001 per response. This pricing is not finalized and may change before GA.

### URL requirements

- Must be a valid HTTP or HTTPS URL.
- Maximum length: 2048 characters.
- Must be publicly accessible from Gcore CDN nodes. The URL is fetched by the CDN, not by the end user's browser.
- URL must not contain unencoded spaces or special characters.

### Fallback behavior

If the custom error page URL is unreachable at the time of the error (e.g., origin is down), the CDN falls back to the default Gcore error page. The fallback is not configurable.

### Caching behavior

**Status: under clarification. Do not document until confirmed.**

Engineering position: the custom error page follows the cache rules of the CDN resource.
Product position: the page should always be served fresh.
Resolution pending. Ticket: [CDN-8842](https://jira.internal/CDN-8842) — assigned to dmitry.k.

## CDN / Origin shielding — Setup guide (internal)

**Last updated:** 2 months ago by marina.s

Origin Shielding is a paid add-on. To enable, customer must contact support or account manager. Internal configuration requires setting `shield_enabled: true` in the resource config and selecting the precache PoP closest to origin.

Billing: charged per GB of shield-to-origin traffic above the plan allowance. See the billing system for current rates.

## CDN / Cache purge — Known issues

**Last updated:** 6 weeks ago by oksana.p

- **Issue:** Purge by pattern with nested wildcards (`/a/*/b/*`) occasionally misses objects on edge nodes in AS-Pacific region. Workaround: use Purge all for that subset.
- **Issue:** Purge history API returns stale status for ~2 minutes after a successful purge. This is a known race condition. Not customer-visible.
- **Status:** Both issues tracked in CDN-8611 and CDN-8629. Fix expected in v2.15.
